# Production-стек на docker compose

Боевой вариант развёртывания для хостов без Kubernetes, наряду с
`helm/corp-llm-gateway/` (вариант для k8s). Английский оригинал: `README.md`.
В этом каталоге лежат:

- **data plane** — `litellm` (прокси со встроенным guardrail) + `redis`
  (Cache B, хранилище per-conversation маппингов) + `postgres` (хранилище
  токенов/конфига команд плюс собственная БД виртуальных ключей и UI litellm);
- **self-hosted Langfuse v3** — `langfuse-web`, `langfuse-worker`,
  `langfuse-postgres`, `clickhouse`, `minio`, `minio-init` и `langfuse-redis`,
  ни один из них не публикует хостовый порт (см. раздел «Langfuse»);
- **конвейер аудита** — `vector`, читающий stdout шлюза и доставляющий записи
  аудита в Langfuse (см. «Конвейер аудита»).

Опциональный фронт на nginx появится в следующей ревизии этого стека — полный
порядок сборки в `docs/plans/20260802-production-compose-corp-ner.md`.

## Какой режим я разворачиваю?

Сначала прочитайте `docs/ops/deployment-modes.ru.md` (EN: `deployment-modes.md`).
Там описаны два **взаимоисключающих** режима аутентификации — корп-API-ключи
против подписки/OAuth — и ровно то, как включаются и выключаются оракул на
корп-vLLM и сервис корп-NER. Оба режима production и оба поднимают **этот** стек.
Кратко:

- **Режим API-ключей (по умолчанию).** `docker compose up -d`.
  `LITELLM_MASTER_KEY` обязателен; разработчики ходят с виртуальными ключами
  LiteLLM. `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` **опциональны** — задавайте
  только те маршруты, которыми пользуетесь, либо ни одного, если ходите только
  в `corp-*`.
- **Режим подписки.** `docker compose -f docker-compose.yml -f
  docker-compose.oauth.yml up -d`. Требует, чтобы `LITELLM_MASTER_KEY` не
  существовал вовсе, обслуживает только `claude-*` и пробрасывает наверх
  собственный токен подписки Anthropic разработчика. Всё, что ниже написано про
  виртуальные ключи, относится только к режиму API-ключей; остальное (аудит,
  NER, оракул, Vector, тома, TLS) в обоих режимах одинаково.
  Корневой `docker-compose.anthropic-oauth.yml` — **демо-вариант** той же идеи
  поверх `docker-compose.demo.yml`, а не боевое развёртывание.
- **Оракул:** `CORP_LLM_ORACLE_ENABLED` (по умолчанию `0`), при `1` нужен
  `CORP_LLM_ENDPOINT`. **Корп-NER:** `CORP_NER_ENABLED` (по умолчанию `0`), при
  `1` нужен `CORP_NER_ENDPOINT`.

## Быстрый старт

```
cd compose
cp .env.example .env
chmod 0600 .env
# отредактировать .env: GATEWAY_IMAGE_TAG, POSTGRES_PASSWORD, LITELLM_MASTER_KEY,
# UI_USERNAME, UI_PASSWORD, тот из ANTHROPIC_API_KEY/OPENAI_API_KEY, чей маршрут
# вы реально используете (ни одного, если только corp-*),
# секреты Langfuse (LANGFUSE_POSTGRES_PASSWORD, LANGFUSE_CLICKHOUSE_PASSWORD,
# MINIO_ROOT_PASSWORD, LANGFUSE_NEXTAUTH_SECRET, LANGFUSE_SALT,
# LANGFUSE_ENCRYPTION_KEY) и ключи ПРОЕКТА Langfuse, с которыми постит конвейер
# аудита (CORP_LANGFUSE_PUBLIC_KEY, CORP_LANGFUSE_SECRET_KEY — см. «Конвейер аудита»)
cp ../src/corp_llm_gateway/tokens/schema.sql postgres/initdb/01-schema.sql
docker compose up -d
docker compose ps                              # подождать ~30-60 с (start_period) до "healthy";
                                               # langfuse-web/worker на чистом томе поднимаются
                                               # ~2 мин, пока идут миграции
curl http://localhost:4000/health/liveliness
```

Пропустить шаг с `01-schema.sql` — тихая ловушка, а не заметная ошибка:
`docker compose ps` покажет всё healthy, `/health/liveliness` ответит, но каждый
реальный запрос упадёт с 500, потому что `corp_tokens`/`team_config` не
существуют. Что делает каждый init-скрипт и как переложить схему после
обновления — в `compose/postgres/initdb/README.md`.

У `GATEWAY_IMAGE_TAG`, `POSTGRES_PASSWORD`, `CORP_LANGFUSE_PUBLIC_KEY` и
`CORP_LANGFUSE_SECRET_KEY` нет значений по умолчанию — `docker compose up`
откажется стартовать с внятным «set X in .env» вместо того, чтобы молча
подняться наполовину настроенным.

`LITELLM_MASTER_KEY`, `UI_USERNAME` и `UI_PASSWORD` тоже обязательны, но их
проверка живёт в entrypoint'е litellm, а не в интерполяции compose, потому что
она должна **зависеть от режима**: в режиме подписки все три обязаны
отсутствовать. В режиме API-ключей их отсутствие — тоже отказ на старте с
указанием переменной, просто на секунду позже, уже при запуске контейнера.

## Сборка из текущей ветки

Значение `GATEWAY_IMAGE_TAG` по умолчанию (`.env.example`) — опубликованный rc,
который старше той ветки, где вы это читаете: фичи, приезжающие сюда (например
`CORP_LLM_STRIP_INBOUND_HEADERS` или интеграция корп-NER из Workstream B), на том
теге просто отсутствуют, пока не собран новый rc и `GATEWAY_IMAGE_TAG` не поднят
на него. Чтобы запустить код текущей ветки, а не опубликованный тег:

```
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

Оверлей собирает NER-профиль **`ru-en`** (build-arg `NER_PROFILE`), а не `base`
из `Dockerfile.gateway`: в `base` нет `en_core_web_md`, и при
`CORP_LLM_REQUIRE_NER=1` (здесь это значение по умолчанию) отсутствующий
английский движок превращает каждый запрос в 503 `E_NER_UNAVAILABLE`. Этот
аргумент убирать нельзя.

**Это удобство для dev/staging, а не замена релизу.** `GATEWAY_IMAGE_TAG` обязан
указывать на rc, содержащий работу Workstream B по корп-NER, прежде чем стек
можно считать production-ready — считайте это релизным гейтом.

## Маршрутизация наверх

`litellm/config.yaml` маршрутизирует по префиксу имени модели: `claude-*` →
нативный `anthropic/`, `gpt-*` → нативный `openai/`, `corp-*` → `hosted_vllm/` на
`CORP_LLM_ENDPOINT`. Креденшелы провайдеров для первых двух берутся из
`ANTHROPIC_API_KEY`/`OPENAI_API_KEY` в `.env`, то есть их держит шлюз, а не
разработчик — почему так, см. «Виртуальные ключи».

`CORP_LLM_ENDPOINT` опционален, но его отсутствие само по себе ничего **не**
выключает: за выключение оракула на корп-LLM отвечает
`CORP_LLM_ORACLE_ENABLED=0` (значение по умолчанию в `.env.example`). При
включённом оракуле и отсутствующем endpoint'е попадание в газеттир уходит на
немаршрутизируемый placeholder-хост из `bootstrap.py`, и запрос падает
fail-closed — на **всех** маршрутах, а не только на `corp-*`. Ставьте
`CORP_LLM_ORACLE_ENABLED=1` только после того, как `CORP_LLM_ENDPOINT` указывает
на доступный корп-vLLM. Самому маршруту `corp-*` endpoint нужен независимо от
флага оракула; без него `corp-*`-запросы падают по одному, а не на загрузке
конфига.

## Виртуальные ключи

**Только режим API-ключей.** В режиме подписки мастер-ключа нет, поэтому нет ни
виртуальных ключей, ни админ-UI; креденшелом служит OAuth-токен разработчика, а
`X-Corp-Auth` остаётся идентичностью команды. См.
`docs/ops/deployment-modes.ru.md`.

Разработчики аутентифицируются **виртуальным ключом LiteLLM**
(`Authorization: Bearer sk-...`), который выпускается из админ-UI или API и
потребляется на прокси — не форвардится и не логируется. Именно поэтому на этом
инстансе заданы `LITELLM_MASTER_KEY` + `DATABASE_URL` + `STORE_MODEL_IN_DB=True`
+ `UI_USERNAME`/`UI_PASSWORD`: виртуальные ключи ЯВЛЯЮТСЯ здесь креденшелом
разработчика и дают отзыв и учёт трафика на человека через админ-UI. Второго,
admin-only инстанса нет — тот паттерн существовал только чтобы держать
мастер-ключ подальше от BYOK-плоскости данных, а BYOK напрямую к
Anthropic/OpenAI невозможен (следующий раздел), так что мотивировавший его
компромисс больше не применим.

`X-Corp-Auth` **не изменился** и с виртуальными ключами не связан — он
по-прежнему несёт через guardrail идентичность команда → профиль → правила →
аудит (`AuthMiddleware`, эта переработка его не трогала). Клиенты шлют **оба**
заголовка на каждый запрос:

- `Authorization: Bearer <виртуальный ключ litellm>` — кому вообще можно
  обращаться к этому прокси, плюс собственный учёт расходов и rate-limit'ов
  litellm.
- `X-Corp-Auth: <корп-токен команды>` — чей профиль/правила/аудит применяются
  внутри guardrail.

## Почему нет BYOK

Две независимые находки, обе уже́ той, что утверждала прошлая ревизия этого
README, — читайте внимательно, механизмы разные.

**(a) Креденшелы нативных `anthropic/`/`openai/` никогда не приходят от
клиента.** Эти провайдеры строят креденшел для upstream из настроенного
`api_key` (`ANTHROPIC_API_KEY`/`OPENAI_API_KEY`) и входящий заголовок
`Authorization` не читают вовсе. Проверено дважды: на litellm 1.85.0
(запинованный образ) и независимо на 1.90.1; см. `examples/compose/README.md`,
раздел «BYOK in local mode (SPIKE finding)».

**(b) Наш собственный guardrail форвардит входящие wire-заголовки независимо от
гейта самого litellm — именно для этого существует
`CORP_LLM_STRIP_INBOUND_HEADERS`.** Гейт litellm
`forward_client_headers_to_llm_api` (`litellm/proxy/litellm_pre_call_utils.py`,
`add_litellm_data_for_backend_llm_call` / `add_headers_to_llm_call_by_model_group`)
в `litellm/config.yaml` корректно не задан — сам litellm клиентские заголовки в
`data["headers"]` не копирует. Но `CorpLlmGuardrail._pre_call_impl` (вызываемый
из `async_pre_call_hook`) выставляет `data["headers"]` **безусловно**, независимо
от этого гейта, а litellm форвардит наверх всё, что оказалось в
`data["headers"]`, как бы оно туда ни попало. Снято с провода против
подставного upstream: `host`, `user-agent`, `accept`, `connection`,
`content-type`, `content-length` и произвольный пробный заголовок доходили до
upstream-вызова на **обоих** маршрутах, `corp-*` и `claude-*`, при выключённом
флаге; при включённом — ни один. То есть `CORP_LLM_STRIP_INBOUND_HEADERS` на
этом стеке несущий, а не зарезервированный no-op — он выставлен в `1` в
`docker-compose.yml`/`.env.example`. `Authorization` он не трогает никогда (см.
`_WIRE_HEADERS_TO_DROP` в `litellm_hook.py` — passthrough BYOK, инвариант #3,
сохранён для тех развёртываний, которые его действительно форвардят).

BYOK (собственный ключ разработчика, пробрасываемый без изменений — инвариант #3
из CLAUDE.md) тем не менее **на этом compose-стеке недоступен вовсе**, ни на
одном маршруте: разработчики аутентифицируются описанным выше виртуальным ключом
litellm, а маршрут `corp-*`/`hosted_vllm/` строит запрос наверх из настроенного
`api_key`/параметров модели ровно так же, как `anthropic/` и `openai/`, а не из
проброшенного клиентского `Authorization`. Точка.

## TLS до корп-vLLM

См. `compose/certs/README.md`. Два разных HTTP-клиента внутри контейнера
`litellm` читают доверие к TLS по-разному: наш собственный `CorpLlmClient`
(httpx) читает `CORP_LLM_CA_BUNDLE` из `.env` (в форме bare-name, поэтому
незаданное значение отсутствует в контейнере вовсе, а не равно пустой строке) —
и область его действия ограничена вызовами корп-vLLM. Клиенты самого litellm
(нативные `anthropic/`, `openai/` И `hosted_vllm/`, все на aiohttp) читают
`SSL_CERT_FILE`, а он **глобален для процесса**: направив его прямо на корп-CA,
вы молча заменили бы хранилище доверия и для
`api.anthropic.com`/`api.openai.com`. Поэтому `SSL_CERT_FILE` из `.env` не
задаётся вообще — entrypoint контейнера собирает на старте комбинированный
bundle (публичные корни certifi плюс `corp-ca-bundle.pem`, если он смонтирован),
и `SSL_CERT_FILE` всегда указывает на него.

## Сервис корп-NER (опционально, выключен)

Удалённый NER-детектор, добавляемый в конец local-first каскада
(`detectors/corp_ner.py`, подключается через `bootstrap.build_corp_ner()`).
**Выключен по умолчанию** — `CORP_NER_ENABLED=0` — и пока он выключен, стек
ведёт себя ровно так же, как до появления этой фичи: ни детектора, ни пробы
готовности. Не путать с `CORP_LLM_REQUIRE_NER` (см. «Настройки окружения»),
который управляет **внутрипроцессными** RU/EN-движками NER и в любом случае
остаётся `1`.

Для включения нужны и `CORP_NER_ENABLED=1`, и `CORP_NER_ENDPOINT` (**базовый**
URL сервиса; клиент сам добавляет `/v1/analyze`). Включено без endpoint'а — это
**отказ на старте**, а не тихий пропуск: `build_corp_ner()` бросает
`ConfigError`, и `gateway-admin config check` сообщает о той же проблеме.

Четыре ключа тюнинга передаются в контейнер **по голому имени**, и именно поэтому
`.env.example` поставляет их закомментированными, а не пустыми:

| ключ | значение по умолчанию в коде | примечания |
|---|---|---|
| `CORP_NER_TIMEOUT_S` | `30` | меньше собственных 60 с сервиса |
| `CORP_NER_MAX_TEXTS` | `256` | текстов в батче (лимит сервиса) |
| `CORP_NER_MAX_INPUT_CHARS` | `200000` | символов в батче; более длинный одиночный текст падает **fail-closed** |
| `CORP_NER_CA_BUNDLE` | не задан | PEM-цепочка для сертификата NER от внутреннего CA |

`CORP_NER_TIMEOUT_S=` (пусто) — это **не** то же самое, что закомментированная
строка. Пустая переменная окружения побеждает конфиг-файл в `config.get()`,
поэтому она перекрывает значение из смонтированного
`/etc/corp-llm-gateway/config.toml` и заставляет `gateway-admin config check`
печатать `''` там, где эффективное значение по умолчанию — `30`. Передача по
голому имени сохраняет смысл «не задано в `.env`» = «здесь не настроено», а
именно это и должна увидеть проверка обязательности `CORP_NER_ENDPOINT`. Та же
логика, что у `CORP_LLM_CA_BUNDLE` выше.

Вызов NER несёт **сырой пользовательский контент**, поэтому проверка TLS для
него не отключается никогда — аварийного выхода в стиле `SSL_VERIFY` для него
нет. Вместо этого направьте `CORP_NER_CA_BUNDLE` на цепочку внутреннего CA
(доступный контейнеру монтированный каталог `compose/certs` для этого годится).

Учтите, что опубликованный `GATEWAY_IMAGE_TAG` старше этой работы — см. «Сборка
из текущей ветки».

## Два UI — какой на какой вопрос отвечает

В стеке два веб-интерфейса. Они не пересекаются, и обращение не к тому — обычная
причина, по которой оператор делает вывод «у шлюза нет данных».

| Вопрос | Где |
|---|---|
| У кого есть виртуальный ключ и действителен ли он? | UI LiteLLM |
| Сколько потратил разработчик/команда и какие у них лимиты? | UI LiteLLM |
| Какие модели отдаёт этот прокси и здоров ли маршрут? | UI LiteLLM |
| Как выглядел запрос `<id>` от начала до конца — латентность, счётчики токенов, ошибка upstream? | Langfuse |
| Был ли этот запрос санитизирован и сколько в нём было замен (`redaction_count`, `finding_label_counts`)? | Langfuse |
| Почему запрос заблокирован (`block_reason`) и чья это команда? | Langfuse |
| Каков аудит-след за последние 90 дней? | Langfuse |

Коротко: **LiteLLM = ключи, модели, расходы. Langfuse = трейсы уровня запроса и
аудит-след.** Ни тот, ни другой никогда не держит оригинальный пользовательский
контент — записи аудита проходят гейт NEVER-полей (`audit/invariants.py`) плюс
VRL-гейт Vector, прежде чем попасть в Langfuse (инвариант #2).

## Langfuse

Self-hosted Langfuse v3, перенесённый из `docker-compose.demo.yml` и укреплённый:

- **каждый секрет приходит из `.env`** — в демо зашиты литералы
  `demo-secret-key-change-in-production` / `demo-salt-change-in-production` /
  нулевой `ENCRYPTION_KEY` / `minioadmin`. Здесь `docker compose up` откажется
  стартовать, пока каждый не задан;
- **ни один сервис Langfuse не публикует хостовый порт** (демо публикует `3000`
  для UI и `9001` для консоли MinIO). Langfuse держит трейсы уровня запроса и
  аудит-след, поэтому добраться до него можно только через профиль nginx (C1)
  или SSH-туннель;
- **именованные тома** для всех stateful-сервисов (`langfuse-postgres-data`,
  `langfuse-clickhouse-data`, `langfuse-clickhouse-logs`, `langfuse-minio-data`,
  `langfuse-redis-data`);
- **точечный `environment:`** на каждый сервис, как и везде в этом файле —
  никакого `env_file:`, который разослал бы
  `POSTGRES_PASSWORD`/`UI_PASSWORD`/ключи провайдеров одинаково в ClickHouse,
  MinIO и Langfuse.

`langfuse-redis` — **отдельный** инстанс Redis, не тот, что у шлюза. Redis шлюза
— это Cache B, который CLAUDE.md называет *обязательным* для десанитизации в
`post_call`, и `redis/redis.conf` ограничивает его `maxmemory 512mb` с
`noeviction`. Разделять его (как делает демо) означает, что backlog приёма
Langfuse может исчерпать этот бюджет и записи Cache B начнут падать с `OOM`:
backlog наблюдаемости сломал бы живую десанитизацию.

Разделение инстансов убирает связь по общей квоте, но **не по хосту**, поэтому
`langfuse-redis` ограничен дважды (`LANGFUSE_REDIS_MAXMEMORY` /
`LANGFUSE_REDIS_MEM_LIMIT` в `.env.example`):

- `--maxmemory 256mb` — собственный лимит данных Redis;
- лимит памяти контейнера `512mb` — страховка по RSS. RSS у Redis идёт *выше*
  `maxmemory` (фрагментация аллокатора, буферы вывода клиентов и
  copy-on-write при форке во время перезаписи AOF), поэтому лимит контейнера
  примерно вдвое больше лимита данных, а не равен ему.

Без обоих неограниченная очередь растёт, пока OOM killer ядра не выберет жертву,
а жертвой с тем же успехом может стать `litellm`, `postgres` или Cache B — то
есть нагрузка наблюдаемости превращается в отказ на пути запроса. Поднимайте оба
вместе; значений по умолчанию хватает на шестизначный backlog задач при
установившемся состоянии в несколько МБ. Оба ключа опциональны в `.env`
(значения по умолчанию живут в `docker-compose.yml`), но **никогда не ставьте
ни один в `0`** — `0` означает «без ограничений» и для Redis, и для docker,
рендерится без предупреждения и возвращает риск для хоста обратно.

`minio-init` — одноразовая задача, создающая bucket для выгрузки событий,
потому что **Langfuse v3 не создаёт его сам**. Без неё `langfuse-web` и
`langfuse-worker` поднимаются healthy, а затем валят каждую запись приёма.

ClickHouse получает `langfuse/clickhouse-config.xml`, который удаляет
`query_log`, `query_thread_log`, `query_views_log` и `text_log`. Эти системные
таблицы хранят сырой текст INSERT — то есть вторую копию содержимого трейсов, с
собственным 30-дневным сроком хранения ClickHouse, в хранилище, за которым не
следит ни один гейт NEVER-полей (инвариант #1).

### Когда очередь Langfuse переполняется

`langfuse-redis` работает с `noeviction` (захардкожено в `docker-compose.yml`,
это не ключ `.env`). Это **решение про потерю данных, а не про размер**: на
пределе Langfuse громко отказывает новым записям приёма вместо того, чтобы молча
удалять элементы очереди для уже принятых событий. Каждый элемент — указатель на
blob события, уже выгруженный в MinIO под `events/`, так что вытеснение не
уничтожило бы полезную нагрузку — но ничто её не перезапишет в очередь, поэтому
трейс никогда не дойдёт до ClickHouse и не появится в аудите. Громкий отказ,
который можно повторить, лучше тихой дыры в аудит-следе.

**Путь запроса это не затрагивает.** Ничто в `pre_call`/`post_call` с этим Redis
не разговаривает: sink аудита у шлюза по умолчанию `stdout` (`CORP_AUDIT_SINK`
на этом стеке не задан — см. `audit/factory.py`), а Vector форвардит оттуда и
повторяет попытки. Эти повторы не бесплатны по умолчанию: они работают потому,
что sink Langfuse в `vector/vector.yaml` настроен с **дисковым буфером**
(`when_full: block`, 1 ГиБ, на томе `vector-data`) и неограниченными повторами с
backoff. Со штатным буфером в памяти или с `when_full: drop_newest` описанные
ниже 5xx вместо этого молча отбрасывали бы записи аудита на уровне Vector — та
же дыра в аудит-следе, ради предотвращения которой существует `noeviction`,
только на шаг выше. Полный путь — в разделе «Конвейер аудита». Даже при sink'е
напрямую в Langfuse fail-policy для `audit_sink` — `continue` (матрица M4), а
неудачная отправка гасится страховкой в `litellm_hook.audit()` — она никогда не
доходит до тела ответа клиенту и не блокирует десанитизацию. То есть переполненная
очередь Langfuse стоит данных наблюдаемости, но никогда — живого трафика.

Последняя фраза и есть весь компромисс, и это задокументированное отступление от
значения `vectorBufferFull` по умолчанию из `docs/security.ru.md` §8 — прочитайте
ниже «Буферизация аудита не fail-closed», прежде чем на это полагаться.

Как это выглядит:

- `langfuse-redis` остаётся **healthy** — `redis-cli ping` это чтение, и на
  пределе он по-прежнему отвечает `PONG`;
- `langfuse-web` пишет ошибки приёма, а его эндпоинт `/api/public/ingestion`
  начинает отдавать 5xx;
- трейсы перестают появляться в UI, при том что запросы продолжают проходить.

Проверить и починить:

```
# действительно ли упёрлись в предел?
docker compose exec langfuse-redis redis-cli info memory | grep -E 'used_memory_human|maxmemory_human'
docker compose exec langfuse-redis redis-cli info keyspace

# жив ли потребитель? полная очередь — это обычно вставший worker, а не малый лимит
docker compose ps langfuse-worker
docker compose logs --tail=100 langfuse-worker
```

Сначала чините потребителя (`langfuse-worker` unhealthy либо лежит
ClickHouse/MinIO) — очередь разойдётся сама, как только он восстановится, а AOF
на `langfuse-redis-data` означает, что перезапуск её не теряет. Поднимать
`LANGFUSE_REDIS_MAXMEMORY` **и** `LANGFUSE_REDIS_MEM_LIMIT` (сохраняя отношение
~2x) стоит только если backlog — это настоящий устойчивый объём, после чего
`docker compose up -d langfuse-redis`. Никогда не «чините» это через `FLUSHALL`:
так выбрасываются принятые, но не обработанные события аудита — ровно тот отказ,
ради предотвращения которого существует `noeviction`.

### Как добраться до UI

Когда появится `--profile nginx` (C1): `langfuse.<домен>` → `langfuse-web:3000`,
и `LANGFUSE_PUBLIC_URL` должен быть этим публичным origin'ом.

До тех пор — SSH-туннель. На хосте ничего не опубликовано, поэтому туннелировать
нужно на адрес контейнера (мост docker маршрутизируется с хоста на Linux):

```
# на сервере
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' \
  "$(docker compose ps -q langfuse-web)"

# с ноутбука, с этим адресом
ssh -N -L 3000:<ip-контейнера>:3000 <user>@<server>
# затем открыть http://localhost:3000
```

`LANGFUSE_PUBLIC_URL` (→ `NEXTAUTH_URL`) обязан совпадать с origin'ом, который
использует **браузер**. Значение по умолчанию `http://localhost:3000` верно для
туннеля и неверно за nginx; одновременно верными они быть не могут, поэтому
меняйте его, когда появится nginx.

### Первый вход

`LANGFUSE_DISABLE_SIGNUP=true` по умолчанию: на свежем инстансе иначе учётку
администратора занял бы тот, кто первым дошёл до UI. Заводите первого
пользователя (и организацию, проект и API-ключи приёма) блоком
`LANGFUSE_INIT_*` из `.env.example` — именно этой парой ключей аутентифицируется
sink аудита Vector, скопированной в `CORP_LANGFUSE_PUBLIC_KEY` /
`CORP_LANGFUSE_SECRET_KEY`. При выключённой регистрации **и** отсутствии
init-пользователя войти будет невозможно; это единственная комбинация, которой
надо избежать.

Проблема курицы и яйца на первом старте: `vector` нужны ключи проекта, а проекта
ещё нет. Чистый выход — headless-инициализация: задайте
`LANGFUSE_INIT_PROJECT_PUBLIC_KEY` / `_SECRET_KEY` значениями, которые вы
сгенерировали, и скопируйте те же два значения в `CORP_LANGFUSE_PUBLIC_KEY` /
`CORP_LANGFUSE_SECRET_KEY`. Тогда всё корректно ещё до старта первого
контейнера, и делать больше ничего не нужно.

Если заводите проект через UI, **не давайте `vector` запуститься до того, как
настоящие ключи окажутся в `.env`.** Langfuse отвечает на неверный ключ `401`, а
HTTP-sink Vector ошибку аутентификации **не повторяет** — 401 не входит в его
множество повторяемых (408/429/5xx), поэтому каждая запись аудита, отправленная
с ключом-заглушкой, логируется как `Events dropped` и теряется. Дисковый буфер
здесь не помогает: запись его уже покинула. Порядок действий поэтому такой:

```
# 1. значения-заглушки в двух ключах CORP_LANGFUSE_* — значений по умолчанию у них
#    нет, поэтому `docker compose config` падает, пока они пустые
# 2. поднять стек БЕЗ форвардера аудита
docker compose up -d --scale vector=0
# 3. создать API-ключи проекта в UI, вписать настоящие значения в .env
# 4. теперь запустить vector
docker compose up -d
```

**Что шаг 4 восстанавливает, а что нет.** У `vector` ещё нет чекпоинта чтения, а
его источник настроен на `read_from: beginning`, поэтому первый запуск проигрывает
заново каждый файл лога, попадающий под glob, с нулевого байта: активный
`-json.log` контейнера `litellm` **и его нумерованные ротации** (`-json.log.1`,
`.2`, … — glob покрывает их именно ради этого). Чего он восстановить не может —
это то, что docker уже выбросил: записи, уехавшие за `LITELLM_LOG_MAX_FILE`,
исчезли с хоста, и никакой повтор до них не доберётся. На практике шаги 2–3 — это
минуты низкого трафика, укладывающиеся далеко внутрь одного файла
`LITELLM_LOG_MAX_SIZE`, так что ничего не теряется; но утверждение ограничено
сроком хранения логов, а не безусловно. См. «Буферизация аудита не fail-closed».

Та же опасность действует и после первого старта: если ключи проекта в Langfuse
ротировали, а `.env` не обновили, `vector` продолжит постить и продолжит терять.
Проверка, которая это вскрывает: `docker compose logs vector | grep "Events dropped"`.

### Восстановление записей, потерянных vector'ом из-за неверного ключа

Это тот самый случай, ради предотвращения которого существует порядок действий
выше, и он требует осознанного восстановления — перезапуск `vector` его **не**
выполняет. Файловый источник ставит чекпоинт по *чтению*, а не по доставке
(сквозные подтверждения выключены), поэтому запись, которую Langfuse отверг с
`401`, уже засчитана как прочитанная и чекпоинт ушёл дальше. При перезапуске
Vector продолжит после этих байт, и они никогда не будут прочитаны заново.

Чтобы их проиграть, удалите чекпоинт файлового источника. Он лежит в `data_dir`
(`/var/lib/vector`, на томе `vector-data`) под именем компонента-источника и
содержит только отпечаток содержимого плюс байтовое смещение на файл — никакого
содержимого логов:

```
# 1. СНАЧАЛА исправить CORP_LANGFUSE_PUBLIC_KEY / CORP_LANGFUSE_SECRET_KEY в .env.
#    Повтор с тем же неверным ключом просто выбросит всё второй раз.
docker compose stop vector

# 2. удалить чекпоинт чтения (дисковый буфер под /var/lib/vector/buffer НЕ трогается —
#    те события всё ещё стоят в очереди на доставку)
docker compose run --rm --no-deps --entrypoint sh vector \
  -c 'rm -f /var/lib/vector/container_logs/checkpoints.json'

# 3. read_from: beginning снова применяется
docker compose up -d vector
docker compose logs vector | grep "Events dropped"   # нового быть не должно
```

Две вещи, которые нужно знать до запуска:

- **Он проигрывает всё, что ещё лежит на диске, а не только потерянное окно.**
  Записи, которые Langfuse уже принял, будут отправлены повторно. У каждой тот же
  `body.id` (это `request_id` шлюза), а API приёма Langfuse делает upsert по
  этому id, поэтому ожидаемый результат — перезапись, а не дубликат трейса;
  проверьте на маленьком окне, прежде чем запускать против нагруженного инстанса.
- **Он достаёт только те байты, которые у docker ещё есть.** Уехавшие в ротацию
  записи невосстановимы, точка: шлюз написал их в stdout и копии не хранил, так
  что после удаления файла проигрывать нечего. Это и есть настоящая причина, по
  которой порядок действий на первом старте начинается с `--scale vector=0`, а
  не полагается на восстановление, и причина, по которой
  `LITELLM_LOG_MAX_SIZE` × `LITELLM_LOG_MAX_FILE` — это решение про размер, а не
  значение, которое можно оставить как есть.

## Конвейер аудита

```
stdout шлюза (StdoutSink)  ->  json-file лог docker  ->  vector  ->  langfuse
```

`CORP_AUDIT_SINK` на этом стеке не задан, поэтому применяется значение по
умолчанию `stdout` из `audit/factory.py`: каждый `AuditEvent` — это одна строка
JSON в stdout контейнера `litellm`. `vector` читает её и постит в
`/api/public/ingestion` Langfuse, аутентифицируясь **проектными** API-ключами
Langfuse `CORP_LANGFUSE_PUBLIC_KEY` / `CORP_LANGFUSE_SECRET_KEY` (не
инфраструктурными секретами `LANGFUSE_*` — откуда они берутся, см. «Первый
вход»). Сервис включён всегда и не закрыт профилем: аудит не опционален, а
ошибка здесь теряет записи аудита.

**Конфиг:** `vector/vector.yaml`, перенесённый из `docker/demo-vector/vector.yaml`.
Трансформы `never_fields_gate` и `audit_only` скопированы из него **дословно** (и
совпадают с `helm/corp-llm-gateway/templates/configmap.yaml`) — это
defence-in-depth для инварианта #2 из CLAUDE.md: они отбрасывают любую запись, в
которой есть ключ mapping/original/credential, до того как она дойдёт до sink'а,
и любую запись не в форме AuditEvent. Не переписывайте и не переставляйте их.

**Никакого docker-сокета.** Демо монтирует `/var/run/docker.sock` и использует
источник Vector `docker_logs`; `docker-compose.demo.yml` предупреждает не
повторять это, потому что сокет — control plane демона docker, а доступ к нему
на чтение равен root на хосте: контейнер с сокетом может запустить
привилегированного соседа с bind-монтированным `/`. Здесь Vector читает
**bind-монтированный только на чтение каталог логов контейнеров**
(`DOCKER_CONTAINERS_DIR`, по умолчанию `/var/lib/docker/containers`) источником
`file`: данные внутрь, никакого control plane, никакого пути на запись. Четыре
следствия, о которых стоит знать:

- glob — это `*/*-json.log` плюс `*/*-json.log.[0-9]` и его двузначная форма,
  поэтому соседние файлы `config.v2.json` / `hostconfig.json`, в которых лежит
  окружение каждого контейнера, не читаются никогда. **Ротированные логи тоже
  читаются.** Docker переименовывает `<id>-json.log` в `<id>-json.log.1` при
  ротации; glob, покрывающий только активный файл, терял бы каждую запись,
  уехавшую в ротацию, пока Vector лежал или отставал. Перечитывание безопасно,
  потому что Vector опознаёт файл по отпечатку содержимого, а не по пути —
  переименованный файл сохраняет свой чекпоинт, и уже отправленные байты
  повторно не уходят. Шаблоны останавливаются на двух цифрах намеренно:
  `…-json.log.*` совпал бы и с `…-json.log.1.gz`, а файловый источник Vector не
  умеет распаковывать. Поэтому сервис пинует `compress: "false"` — см. последний
  пункт;
- источник видит логи **всех** контейнеров, а не только `litellm`, потому что
  каталог логов ключуется по id контейнера и glob сузить нельзя. Ограничение
  делается на трансформ позже — см. «Граница идентичности контейнера»;
- нужен **драйвер логов `json-file`**, поэтому сервис `litellm` пинует
  `logging.driver: json-file`, а не наследует умолчание хоста. При общесистемном
  драйвере `local`, `journald` или удалённом остальные контейнеры не производят
  файлов `*-json.log`, но `litellm` — единственный, который читает этот
  конвейер, — производит;
- **пиновка драйвера стоит политики ротации от демона, поэтому сервис задаёт
  свою.** Docker сливает log-opts уровня демона в контейнер *только когда
  драйвер контейнера совпадает с драйвером демона по умолчанию* (moby
  `daemon/logs.go`, `mergeAndVerifyLogConfig` — цикл копирования находится
  внутри `if cfg.Type == daemon.defaultLogConfig.Type`). На хосте с умолчанием
  `local` пинованный сервис не унаследовал бы ничего, а собственное умолчание
  `max-size` у `json-file` — `-1`: никакой ротации, неограниченный лог аудита на
  том же диске, что Cache B и Postgres. `logging.options` задаёт `max-size` /
  `max-file` явно (`LITELLM_LOG_MAX_SIZE` / `LITELLM_LOG_MAX_FILE`, по умолчанию
  `100m` × `10` ≈ дисковый буфер в 1 ГиБ). Их удаление **не** возвращает эту
  задачу демону;
- **то же слияние работает и в обратную сторону для `compress`, поэтому сервис
  пинует его выключенным.** На хосте, у которого драйвер демона по умолчанию —
  `json-file` с `compress=true`, слияние копирует эту опцию в любой контейнер,
  который её не назвал; docker тогда пишет ротации как `…-json.log.1.gz`, под
  glob Vector они не подпадают, а если бы подпали — прочитать он их не смог бы.
  Каждая запись, уехавшая в ротацию, пока Vector лежал или был под
  back-pressure, терялась бы молча. Замерено на демоне docker 29.7.1 с
  умолчанием json-file + `max-size=1k`/`max-file=4`/`compress=true`: контейнер,
  пинующий только два размерных параметра, ротировался в
  `…-json.log.{1,2,3}.gz`; добавление `compress: "false"` дало обычные
  `…-json.log.{1,2,3}`. Это не ключ `.env` — расширение glob'а Vector до
  `…-json.log.*` не альтернативное решение, оно лишь подберёт файлы, которые
  Vector всё равно не распакует.

**Граница идентичности контейнера.** `docker-compose.yml` вешает на сервис
`litellm` метку `com.corp-llm-gateway.audit-source: gateway-stdout` и называет
эту метку в `logging.options.labels` того же сервиса. Именно вторая половина
заставляет драйвер json-file копировать метку в каждую запись лога, которую он
пишет для этого контейнера:

```
{"log":"...","stream":"stdout",
 "attrs":{"com.corp-llm-gateway.audit-source":"gateway-stdout"},"time":"..."}
```

Первый трансформ Vector, `gateway_container_only`, пропускает строку только при
наличии этого штампа в `attrs` — до распаковки содержимого приложения и до того,
как её увидит что-либо ниже по конвейеру. То есть чтобы накормить конвейер
аудита, нужен контроль над созданием контейнеров на этом хосте, а не просто
возможность напечатать строку. Все три части (метка, опция логирования, фильтр)
— один механизм; уберите любую, и конвейер либо замолчит, либо потеряет свою
границу.

**Это защита от ошибки конфигурации, а не граница безопасности — и разница здесь
является production-требованием.** Имя метки и её значение публичны, напечатаны
в этом файле и в конфиге; ничего секретного или проверяемого в них нет. Любой,
кто может выполнить `docker run` на этом хосте, может запустить контейнер с той
же `--label com.corp-llm-gateway.audit-source=gateway-stdout` и тем же
`--log-opt labels=com.corp-llm-gateway.audit-source`, напечатать JSON в форме
`AuditEvent` и пройти этот фильтр, гейт NEVER-полей и `audit_only` — то есть
подделать записи аудита в Langfuse. Фильтр поднимает планку с «может написать
строку в лог» до «может запустить здесь контейнер», и не более.

Итого: **никакого недоверенного `docker run` на хосте, где работает этот стек.**
Считайте членство в группе `docker` (и любой CI-раннер, агент или sidecar с
доступом к сокету) равносильным праву записи в аудит-след и ограничивайте
соответственно. Это ограничение подхода «читать логи всех контейнеров»; закрыть
его как следует можно только приватным каналом, в который может писать один
`litellm` — выделенным bind-монтированным файлом аудита или unix-сокетом, — а
это изменение в sink'е аудита в `src/`, а не в этом стеке. Зафиксировано в
`docs/security.ru.md` §8.2.

`audit_only` остаётся тем же, чем был всегда: **схемным** гейтом, который не
пускает не-`AuditEvent`-строки (собственные JSON-обёртки litellm, access-логи
uvicorn). Он не является границей доверия — `request_id` и `redaction_count` это
два обычных ключа, и до появления этого фильтра любой соседний контейнер,
написавший JSON-строку с ними, форвардился в хранилище аудита.

Vector работает с read-only корневой ФС и сброшенными capabilities. Он остаётся
root (умолчание образа), потому что каталог логов имеет режим `0710 root:root`;
добавлять `user:` тут некуда.

**Доставка устойчива к временным сбоям.** Чекпоинты чтения и дисковый буфер
sink'а живут на именованном томе `vector-data`, поэтому перезапуск Vector
продолжает ровно с того байта, на котором остановился — записи, сделанные пока
он лежал, доставляются, а не пропускаются, и ни одна не отправляется дважды.
Sink Langfuse буферизует на диск с `when_full: block` и повторяет попытки
бесконечно с backoff; почему эта комбинация несущая, а не значение по умолчанию,
см. «Когда очередь Langfuse переполняется». Если дисковый буфер всё же
заполнится, Vector создаст back-pressure файловому источнику и перестанет
читать — записи останутся в лог-файлах docker и будут подхвачены с чекпоинта,
как только Langfuse восстановится.

«Временным» — ключевое слово. HTTP-sink Vector повторяет `408`, `429` и `5xx`;
любой другой `4xx` окончателен, и запись отбрасывается с ошибкой
`Events dropped` в `docker compose logs vector`. На практике это значит, что
**неверный или ротированный ключ `CORP_LANGFUSE_*`** (`401`) — это тихая потеря
аудита, а не повтор; см. «Первый вход». В Vector 0.53 нет настройки, меняющей
множество повторяемых кодов, а его блок `request:` молча игнорирует неизвестные
ключи, так что выдуманная опция там пройдёт валидацию и ничего не сделает.

### Буферизация аудита не fail-closed

`docs/security.ru.md` §8 указывает `vectorBufferFull` как **fail-closed (503) по
умолчанию, с доступной per-team опцией `audit_buffer_full=continue`**. **Этот
стек берёт опцию `continue` и иначе не может.** Прямым текстом: вставший путь
аудита здесь **не** останавливает egress запросов.

Почему: доставка аудита происходит вне процесса. `CORP_AUDIT_SINK` не задан,
поэтому единственное действие шлюза по аудиту — записать строку в собственный
stdout, что всегда успешно. Vector читает этот лог-файл потом, из другого
контейнера. Пути сигнала из состояния буфера Vector обратно в
`pre_call`/`post_call` нет, так что ничто на пути запроса не видит затор, а
`when_full: block` останавливает только *чтение* Vector — до шлюза он не
доходит. Настоящий fail-closed на пути запроса требует гейта по
здоровью/буферу внутри `src/corp_llm_gateway/`; его пока нет.

Это осознанное отступление от значения матрицы по умолчанию, а не недосмотр, и
это цена того, что процесс шлюза не зависит от здоровья форвардера аудита.
Остаточный риск: пока Langfuse недоступен, принятые записи аудита живут
**только в json-file логах docker контейнера `litellm`** (плюс то, что уже
попало в дисковый буфер Vector). То есть реальную границу долговечности задаёт
срок хранения логов, а не дисковый буфер. Glob Vector действительно следует за
нумерованными ротациями (`-json.log.1`, `.2`, …), поэтому одна ротация больше
ничего не выбрасывает; но файл, уехавший за `LITELLM_LOG_MAX_FILE`, удаляется
docker'ом, и эти записи аудита потеряны навсегда.

Две вещи, которые оператор обязан настроить до ввода в эксплуатацию:

1. **Рассчитать срок хранения логов docker** для контейнера `litellm` под
   максимальную недоступность Langfuse, которую вы намерены пережить, при вашем
   объёме аудита. Ручки — `LITELLM_LOG_MAX_SIZE` / `LITELLM_LOG_MAX_FILE` (по
   умолчанию `100m` × `10`), которые сервис задаёт в собственных
   `logging.options`. **Не задавайте их в `log-opts` демона в расчёте, что они
   применятся** — docker сливает log-opts уровня демона в контейнер только
   когда драйвер контейнера совпадает с драйвером демона по умолчанию, а этот
   сервис пинует `json-file`, потому что конвейеру это нужно. На хосте с
   умолчанием `local` или `journald` политика демона для этого контейнера молча
   игнорируется. Произведение `max-size × max-file` обязано превышать объём
   аудита за это окно; `CORP_VECTOR_LANGFUSE_BUFFER_BYTES` должен быть рассчитан
   на то же окно (значения по умолчанию совпадают на ~1 ГиБ).
2. **Настроить алерт на вставший или теряющий путь аудита.** За вас этого не
   делает ничто — healthcheck `vector` доказывает только, что процесс жив, а
   `langfuse-redis` отвечает `PING` и будучи полным. Три проверки, которые это
   вскрывают:

```
# забуферизовано, но не доставлено — растёт, пока langfuse недоступен
docker compose exec vector du -sh /var/lib/vector/buffer

# отброшено совсем — неверный ключ или любой другой неповторяемый ответ
docker compose logs vector | grep "Events dropped"

# сколько осталось запаса по ротации? один `-json.log` плюс N файлов
# `-json.log.<n>`; на LITELLM_LOG_MAX_FILE следующая ротация УДАЛЯЕТ самый
# старый, а вместе с ним любые записи аудита, которые vector не успел прочитать
docker compose exec vector ls -l \
  "$(dirname "$(docker inspect -f '{{.LogPath}}' "$(docker compose ps -q litellm)")")"

# насколько vector отстаёт? один {fingerprint, position} на каждый прочитанный
# файл — только смещения, никогда содержимое логов
docker compose exec vector cat /var/lib/vector/container_logs/checkpoints.json
```

**Длинные записи собираются обратно.** Драйвер `json-file` разбивает любую
строку вывода длиннее 16 КиБ на несколько записей, и только последняя
заканчивается переводом строки. Без склейки обе половины не распарсились бы и
`audit_only` их отбросил бы — тихая дыра ровно для самых больших записей аудита
(запрос с длинным `placeholder_list`). Reduce `merge_partial_lines` их
склеивает; то же самое источник `docker_logs` Vector делает сам через
`auto_partial_merge`.

**Sink-и S3 и SIEM поставляются ВЫКЛЮЧЕННЫМИ.** `vector/sinks-s3.yaml`
(долговременный архив) и `vector/sinks-siem.yaml` (форвардер) — отдельные файлы
конфигурации, загружаемые только при `CORP_AUDIT_S3_ENABLED=1` /
`CORP_AUDIT_SIEM_ENABLED=1`. Vector сливает каждый файл `--config` в одну
топологию, поэтому оба цепляются к тому же трансформу `audit_only` и наследуют
гейт NEVER-полей. Корпоративный SIEM-эндпоинт и его схема аутентификации всё ещё
открытый вопрос, поэтому у этого файла нет endpoint'а по умолчанию: включение
без `CORP_AUDIT_SIEM_URL` заставит Vector отказаться стартовать, а не постить
записи аудита куда попало. То же самое с `CORP_AUDIT_S3_BUCKET` /
`CORP_AUDIT_S3_REGION`.

Одна особенность Vector при правке этих файлов: **он интерполирует ссылки
`${VAR}` и внутри YAML-комментариев**, поэтому закомментированный пример,
называющий незаданную переменную, ломает загрузку конфига. Описывайте такие
опции прозой.

Проверить изменение до развёртывания:

```
docker run --rm -v "$PWD/vector:/etc/vector:ro" \
  -e CORP_LANGFUSE_PUBLIC_KEY=x -e CORP_LANGFUSE_SECRET_KEY=x \
  timberio/vector:0.53.0-alpine validate --no-environment /etc/vector/vector.yaml
```

## Postgres

Две базы на одном сервисе `postgres`: `$POSTGRES_DB` (по умолчанию `gateway` —
наша схема tokens/team_config) и `litellm` (собственное хранилище виртуальных
ключей и учёток UI, создаётся закоммиченным
`compose/postgres/initdb/00-create-litellm-db.sh`). Как раскладывается схема
`$POSTGRES_DB` — см. `compose/postgres/initdb/README.md` (она в git-ignore, её
никогда не коммитят, чтобы она не разъехалась с
`src/corp_llm_gateway/tokens/schema.sql`).

## Привязка к loopback

Порт `litellm` публикуется на `127.0.0.1`, а не на `0.0.0.0`. Пока не появился
профиль nginx (`--profile nginx`), перед стеком нет TLS, а виртуальные ключи и
`X-Corp-Auth` иначе ходили бы по серверной сети открытым текстом. Это
единственный опубликованный порт в стеке: ни один сервис Langfuse не публикует
порта вовсе (см. «Langfuse»), а API Vector привязан к `127.0.0.1` *внутри* его
собственного контейнера — исключительно чтобы до него дотягивался healthcheck.

## Долговечность

Каждый stateful-сервис использует именованный том, поэтому `docker compose down`
(без `-v`) сохраняет маппинги, токены/конфиг команд, виртуальные ключи и всю
историю трейсов/аудита Langfuse между перезапусками — в отличие от
«прогулочной» посадки `docker-compose.demo.yml`. У самого `litellm` именованного
тома нет; он stateless (конфиг и сертификаты — bind-монтирования только на
чтение), а его состояние уже живёт в `redis`/`postgres` выше. Redis настроен на
`noeviction` (`compose/redis/redis.conf`): Cache B — это обязательное по
CLAUDE.md хранилище per-conversation маппингов для десанитизации в `post_call`,
поэтому Redis с нехваткой памяти обязан падать громко (ошибки `OOM`), а не
молча вытеснять живые маппинги и возвращать разработчику текст с
placeholder'ами.

## Обновление с более раннего развёртывания

Если вы уже запускали этот стек до переработки виртуальных ключей litellm (когда
не было `compose/postgres/initdb/00-create-litellm-db.sh`), в вашем томе
`postgres` нет базы `litellm`, и контейнер `litellm` падает на старте —
скрипты `docker-entrypoint-initdb.d` отрабатывают один раз, на пустом томе.
Способ исправления (пересоздание либо ручной `CREATE DATABASE`) — в
`compose/postgres/initdb/README.md`, раздел «Upgrading a pre-existing
deployment».

## Настройки окружения

`CORP_ENV=production` взводит защиту F9 (`config.py`, `is_prod()`):
операторский `SSL_VERIFY=false` на вызове **оракула** корп-LLM отклоняется, а не
молча отключает там проверку TLS. F9 доходит до этой защиты только через
`build_corp_llm_client()`, который выполняется лишь при
`CORP_LLM_ORACLE_ENABLED=1` — на этом стеке выключенном по умолчанию, — поэтому
считайте её узкой защитой только для оракула, а не всеобщей (см. «Проверка TLS
включена всегда» ниже). `CORP_LLM_REQUIRE_NER=1` заставляет самоотключившийся
движок NER падать fail-closed (`NerUnavailableError`), а не молча возвращать
пустой список находок и выпускать PERSON/ORG наружу (F2). Оба выставлены по
умолчанию в `.env.example`; для реального развёртывания их не снимать.

**Проверка TLS включена всегда.** `SSL_VERIFY` захардкожен в `true` в
`docker-compose.yml` и **не** является ключом `.env` — собственный
`get_ssl_verify()` litellm читает ту же переменную напрямую, с *более высоким*
приоритетом, чем `SSL_CERT_FILE`, для каждого upstream-провайдера
(`anthropic/`, `openai/`, `hosted_vllm/`), и никакой защиты по `CORP_ENV` на
этом чтении нет. Настраиваемый оператором `SSL_VERIFY=false` здесь молча
отключил бы проверку сертификатов по всему стеку, а не только для оракула. См.
`docs/security.ru.md`, «Известные пробелы/следующие шаги» — расширение F9 на
чтение litellm это доработка в `src`, вне области этого compose-стека.

**`CORP_LLM_ORACLE_ENABLED` и `CORP_LLM_LOCAL_FIRST` связаны.**
`bootstrap.build_guardrail()` бросает `ConfigError(NO_OP_SANITIZER_MESSAGE)` на
старте, если выключены оба — шлюз отказывается работать как no-op-санитайзер.
Этот стек оставляет `CORP_LLM_LOCAL_FIRST` незаданным (умолчание в
`settings.py` — `"1"`), поэтому посадка по умолчанию безопасна; не ставьте его в
`0` в `.env`, не выставив одновременно `CORP_LLM_ORACLE_ENABLED=1`, иначе
контейнер не поднимется и других предупреждений не будет.
