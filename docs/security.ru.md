# Модель безопасности

Как corp-llm-gateway удерживает PII внутри корпоративного периметра, что он
санитизирует и куда смотреть при расследовании инцидента.

Читать вместе с: [`audit-schema.md`](audit-schema.ru.md) (источник истины по полям),
[`x-corp-auth.md`](x-corp-auth.ru.md), [`conversation-id.md`](conversation-id.ru.md),
[`ops/runbook.md`](ops/runbook.ru.md) и планом
[`plans/20260507-external-sanitizer-gateway-v1.md`](plans/20260507-external-sanitizer-gateway-v1.md)
(M4 fail-policy матрица — единственный источник истины по поведению при отказах).

## 1. Обзор и модель угроз

Шлюз располагается между инстансами Claude Code разработчиков и upstream LLM
API (`api.anthropic.com` / `api.openai.com`). На `pre_call` он направляет
контент запроса через корп-внутреннюю санитизирующую LLM, заменяя PII /
регулируемые термины плейсхолдерами `[LABEL_NNN]` **до того, как хоть один байт
покинет корпоративный периметр**. На обратном пути собственный ASGI-слой шлюза
разворачивает плейсхолдеры обратно в оригиналы по маппингу запроса, который
никогда не покидает шлюз и никогда не попадает в litellm (§15).

| Свойство | Поведение |
|---|---|
| Критерий успеха | **Ноль подтверждённых инцидентов утечки** за 90 дней после GA (не подлежит обсуждению) |
| Поведение при отказе | **Fail-closed** для пути санитизации: если corp-LLM не может отработать, запрос отклоняется (503 `E_CORP_LLM_DOWN`), а не пробрасывается без санитизации (`litellm_hook.py` `pre_call`) |
| BYOK `Authorization` | `Authorization: Bearer …` разработчика (ключ Anthropic/OpenAI) пробрасывается наверх (upstream) **без изменений** и **никогда не логируется** — это NEVER-поле в гейте аудита. Опциональные мосты подписочной аутентификации также только читают этот bearer, не переписывая его; см. §13 |
| `X-Corp-Auth` | Корп-токен поглощается в `pre_call` (`AuthMiddleware.strip_corp_token`), срезается из пробрасываемых заголовков и **никогда не попадает в аудит-конвейер** — NEVER-поле |

Эшелонированная защита (defense in depth): гарантия отсутствия утечек
обеспечивается на нескольких независимых уровнях (биекция плейсхолдеров,
внутрипроцессный NEVER-гейт, Vector VRL-гейт и инвариант-тест M1-14), так что
любая одиночная регрессия ловится дальше по цепочке.

## 2. Что санитизируется (покрытие контента)

Обходчик контента (content walker) `sanitizer/content_blocks.py` проходит каждую
форму запроса. `pre_call` вызывает его для каждого `content` сообщения плюс
верхнеуровневого поля Anthropic `system`; `collect_text` зеркалит тот же обход в
режиме только-чтение, чтобы пред-скан видел ровно то, что будет санитизировано.

### Покрыто (санитизируется на egress)

| Форма | Что санитизируется |
|---|---|
| Верхнеуровневая строка `content` | Вся строка |
| Блок `text` (`{"type":"text","text":…}`) | Значение `text` |
| Блок `tool_result` | Его `content`, **рекурсивно** (повторно входит в `sanitize_content`) |
| `tool_use.input` | Строковые **листья** входного JSON-дерева, рекурсивно; **ключи** словаря (имена аргументов тула) сохраняются; нестроковые скаляры проходят насквозь |
| Блок `document` | `title`, `context`; `source.data` при `source.type == "text"`; `source.content` рекурсивно при `source.type == "content"` |
| Верхнеуровневый `system` Anthropic | Всё поле (строка или список блоков) |
| Мультимодальные части `content` OpenAI | `text`-части (текстовые блоки в списке); прочие типы частей проходят насквозь |

### Отклоняется на route gate (никогда не доходит до провайдера)

Покрытие выше описывает, что guardrail переписывает на тех маршрутах, где он
работает. Есть класс хендлеров litellm, которые принимают пользовательский текст
и вообще не вызывают `pre_call_hook`: три подтверждённых обхода (оба счётчика
токенов и Responses WebSocket) и все прочие хендлеры без хука, которые таблица
отклоняет. Ещё один класс доходит до хука, но не переписывается, потому что хук
читает только `messages` / `input`. С появлением route gate (§14) все они
отклоняются до того, как запрос увидит роутер litellm. Это default-deny: маршрут,
который litellm добавит в будущем релизе, тоже отклоняется, пока его не
классифицируют.

| Маршрут | Почему отклоняется | Код причины |
|---|---|---|
| `POST /v1/messages/count_tokens` | Хука нет: сырые `messages`/`system`/`tools` уходили в CountTokens API Anthropic без санитизации и без аудита. Claude Code вызывает его для индикатора контекста | `route_gate_listed` |
| `POST /v1/responses/input_tokens` | Хука нет: сырой Responses `input` уходил в счётчик токенов провайдера | `route_gate_listed` |
| `WEBSOCKET /v1/responses`, `/v1/realtime`, `/openai/v1/realtime` | Рукопожатие доходит до хука без контента, а ни один следующий кадр `response.create` до него не доходит. Отклоняется на рукопожатии, до connect | `route_gate_websocket` |
| `POST /utils/token_counter` | Отклоняется при каждом вызове, какой бы ни была строка запроса: гейт классифицирует только `(method, path)`. `call_endpoint` — **параметр** запроса, поэтому `?call_endpoint=true` отправляет сырые `messages`/`prompt` в API подсчёта провайдера с пути, который выглядит как админская утилита | `route_gate_listed` |
| `POST /queue/chat/completions`, `/mcp-rest/tools/call`, `/search/{tool}`, `/apply_guardrail`, `/health/test_connection` | Принимают пользовательский текст и доходят до провайдера без хука | `route_gate_listed` |
| `POST /v1/completions` | Доходит до хука, но хук не читает `prompt`, поэтому ничего не переписывается | `route_gate_listed` |
| `/v1/embeddings`, `/v1/moderations`, `/v1/audio/speech`, деревья нативного passthrough провайдеров (`/anthropic/…`, `/openai/…`, `/{provider}/…`) и остальные `_NON_CHAT_INPUT_CALL_TYPES` (`litellm_hook.py:2099`) | Доходят до хука как задокументированный набор без переписывания: раньше только DLP-скан, теперь отклоняются полностью — DLP-скан блокирует *известный* паттерн, но не санитизирует | `route_gate_listed` |
| `POST /api/event_logging/batch` | Пакет телеметрии Claude Code. Хука нет, и в нём то, что клиент решил туда положить | `route_gate_listed` |
| management-контур litellm: админский JSON API (`/key/*`, `/team/*`, `/model/*`, `/policies*`, `/guardrails*`, …), аналитика расходов, login / SSO / приглашения, публичный каталог, ассеты UI, `GET /`, lazy warm-up и все маршруты `/health/*`, кроме трёх проб | Отклоняется намеренно: идентичность — это `X-Corp-Auth` в собственном хранилище шлюза, наблюдаемость — Langfuse, так что в рантайме ничего из этого не нужно. При этом несколько таких маршрутов могут выключить санитайзер после старта (§14, «Управляющая поверхность запрещена») | `route_gate_listed` |
| Всё, чего нет в таблице, включая смонтированные под-приложения litellm (админский **UI**, `/swagger`, `/docs`, `/openapi.json`) | Default-deny. `ast` не видит внутрь смонтированного ASGI-приложения, поэтому записи оно не получает | `route_gate_unlisted` |

**Поэтому предварительный подсчёт токенов недоступен** — осознанный компромисс,
см. §11 (i). `usage.input_tokens` в каждом
реальном ходе — точный счёт после санитизации; для индикатора Claude Code
использует собственную оценку.

### Не санитизируется / отложено

| Форма | Почему это допустимо / статус |
|---|---|
| `source` блока `document` с `type` `base64` / `url` | Бинарный или вне-скоуп контент; оставлен без изменений (намеренно) |
| Блоки `image` / `image_url` | Бинарная нагрузка или низкорисковый URL; проходит насквозь |
| Блоки `thinking` / `redacted_thinking` | **Намеренно** проходят без изменений — Anthropic подписывает thinking-блоки и отклоняет изменённые при multi-turn-переигрывании, поэтому их нельзя переписывать; модель в любом случае видит только плейсхолдеры (до неё не доходит ни один оригинал). Корректно by design, а не пробел. |
| Chat `messages[].name` (любая роль) | Имя участника, свободный текст; не переписывается и не входит в скан Stage 5, поэтому доходит до провайдера как есть. **Открыто — доработка.** |
| Chat `prediction.content` (Predicted Outputs) | Свободный текст; не переписывается и не входит в скан Stage 5, поэтому доходит до провайдера как есть. **Открыто — доработка.** |
| Responses `prompt.variables` (значения шаблона сохранённого промпта) | Свободный текст; не переписывается и не входит в скан Stage 5, поэтому доходит до провайдера как есть. **Открыто — доработка.** |
| `citations[]` текстового блока Anthropic (`cited_text`, `document_title`) | На стороне запроса не переписывается и не входит в скан Stage 5 (цитата, собранная клиентом, уходит как есть); на стороне ответа не восстанавливается (цитата от провайдера приходит клиенту с плейсхолдерами). **Открыто — доработка.** |

Де-санитизация на стороне ответа (обратный путь) восстанавливает оригиналы в
потоковом и унарном **text**, во **входе `tool_use`** (`input_json_delta`,
JSON-экранированный, чтобы пересобранный JSON оставался валидным) и в content
OpenAI; только `thinking` намеренно оставлен без изменений (см. строку выше).
Она выполняется в ASGI-слое шлюза, вне litellm, поэтому внутри litellm ни один
оригинал не виден (§15).

Политика превышения размера (F1, ранее M1-11): когда отдельный текстовый лист
превышает `guardrail.contentSizeThresholdBytes` (по умолчанию `102400`), **старый
код доставлял лист без санитизации — это подтверждённая утечка, и так больше не
работает.** Поведение задаётся `CORP_LLM_OVERSIZE_POLICY`:

- **`fail-closed` (по умолчанию)** — отказ в egress, HTTP 422
  `E_OVERSIZE_BLOCKED` (`OversizeContentError` несёт только размеры в байтах,
  никогда не сырой контент). Ни один оригинал не попадает ни в тело ошибки, ни
  в логи, ни наверх.
- **`chunk`** — резать лист на перекрывающиеся окна и санитизировать.
  Regex/checksum-детекция **линейна и идёт по полному тексту** (поэтому секрет
  с неограниченным паттерном — JWT, `Bearer {20,}`, `sk-{32,}`, URL БД — не
  может «проскочить» по шву между окнами, H1); нарезается только ограниченный
  по размеру проход NER + газеттир + условный оракул, с перекрытием, которое
  удерживает ограниченную сущность внутри одного окна. Один
  `RequestPlaceholderAllocator` сохраняет биекцию в пределах запроса.
- **`deliver-flag`** — переслать оригинал, но ТОЛЬКО для команды из списка
  `CORP_LLM_OVERSIZE_DELIVER_TEAMS` и ТОЛЬКО если полное пересканирование (та
  же детекция, что и на обычном пути) чистое; любая находка откатывает к
  fail-closed. Доставленный лист помечается `block_reason="oversize:delivered"`
  в аудит-записи и логируется как
  `litellm_pre_call_system_oversize_delivered` — то есть каждый такой egress
  аудируем.

## 3. Модель плейсхолдеров

Corp-LLM возвращает пары `(original, placeholder)`, где каждый плейсхолдер — это
`[LABEL_NNN]` (например, `[EMAIL_001]`). Далее путь pre-call обеспечивает строгую
per-request **биекцию** через `RequestPlaceholderAllocator`
(`sanitizer/placeholder_allocator.py`), по одному экземпляру allocator на запрос:

- **Один и тот же оригинал → один токен.** Повторяющийся оригинал (даже в разных
  сегментах сообщений и поле `system`) переиспользует свой первый плейсхолдер, так
  что upstream-модель видит для него один согласованный токен.
- **Разные оригиналы → разные токены.** Corp-LLM нумерует плейсхолдеры каждого
  сегмента с `[LABEL_001]` независимо, поэтому два разных оригинала могут
  столкнуться на одном токене; при коллизии allocator **выпускает новый лейбл в
  том же семействе** (`placeholder_family`, например, другой `EMAIL_NNN`). Без
  этого де-санитизация (по ключу-плейсхолдеру) смогла бы восстановить только один
  из них.
- **Подстановка по убыванию длины (M1-9).** И прямой (`apply_pairs`), и обратный
  (`_apply_reverse_to_response`, `sort_placeholders_by_descending_length`) проходы
  сортируют длиннейшие-первыми, чтобы короткий токен не затенял более длинный.

### Пред-скан входа (запрет литералов, введённых пользователем)

Перед санитизацией `pre_call` сканирует вход (`collect_text` →
`find_placeholder_literals`) на любую подстроку формы `[LABEL_NNN]`, введённую
пользователем **буквально**. Каждый такой литерал передаётся в
`allocator.forbid(...)`, чтобы реальному редактированию никогда не был назначен
токен, который пользователь уже ввёл дословно, — иначе литерал пользователя был
бы развёрнут в несвязанный оригинал на обратном проходе. Сегодня
`conversation_id == request_id`, поэтому коллизия остаётся в пределах одного
запроса, но это стало бы cross-context утечкой, если `conversation_id`
расширится (см. [`conversation-id.md`](conversation-id.ru.md)). При обнаружении
любого литерала `pre_call` логирует **не содержащий контента** маркер:

```
litellm_pre_call_input_placeholder_literal_detected request_id=… count=N
```

что также является сигналом зондирования санитайзера (см. §10).

### Защита по глубине (fail-closed)

Рекурсивный обход JSON ограничивает вложенность на `_MAX_JSON_DEPTH = 64`. На
пути **санитизации** превышение поднимает `ContentTooDeepError`, который
`pre_call` отображает в **`400 E_BAD_REQUEST`** («request content nesting too
deep») — то есть срабатывает **fail-closed**, никогда не пробрасывая контент,
который обходчик не смог полностью пройти. (Обратный обход/де-санитизация просто
прекращает спуск за пределом и возвращает значение как есть, поскольку к этому
моменту всё уже плейсхолдеры.)

## 4. Аудит-конвейер

Поток на запрос:

```
one record per request builds AuditEvent (audit/event.py — NEVER fields are not
  even constructible as attributes): a route-gate or limiter refusal, a pre-call
  refusal, or the terminal record (route_gate/terminal_audit.py, §15)
   ↓
AuditLogger.emit() → _serialize() → assert_no_never_fields()  [in-process gate]
   ↓
StdoutSink writes ONE JSON line to pod stdout (audit/sinks.py)
   ↓
Vector tails it  (prod: stdin source; demo: docker_logs source)
   ↓
parse JSON → NEVER-fields VRL gate (defense in depth)
   ↓
keep only AuditEvent-shaped records (have request_id AND redaction_count)
   ↓
reshape → sinks (Langfuse, S3; SIEM designed, see §6)
```

### ALWAYS-поля (эмитятся в каждой записи)

Точный набор из `audit/logger.py::_serialize`:

`timestamp`, `request_id`, `user_id`, `team_id`, `provider`, `model`,
`latency_ms`, `prompt_token_count`, `completion_token_count`,
`redaction_count`, `finding_label_counts`, `cache_a_hit`, `gateway_version`,
`status`.

> `gateway_version` инъецируется логгером (аргумент конструктора), а не
> переносится на `AuditEvent`. Отдельный `LangfuseSink._event_to_record` его
> **не** устанавливает, поэтому запись, поданная напрямую в этот sink (не через
> `AuditLogger`), не имеет `gateway_version`.

### CONDITIONAL-поля (присутствуют только когда применимо)

| Поле | Присутствует когда |
|---|---|
| `placeholder_list` | `redaction_count > 0` (уникальный + отсортированный список только строк-плейсхолдеров) |
| `error_code` | `status != "ok"` |
| `corp_llm_latency_ms` | был задействован путь corp-LLM |
| `pre_pass_latency_ms` | был задействован путь pre-pass |
| `audit_buffer_full` | присутствует сигнал буфера Vector |

См. [`audit-schema.md`](audit-schema.ru.md) для полной схемы и типов (это источник
истины по полям).

### Семантика счётчиков

- `redaction_count` = число **РАЗЛИЧНЫХ** секретов (по одному на каждый различный
  оригинал, подсчитанных как различные канонические плейсхолдеры в
  `_merge_into_state`) — **не** счётчик вхождений.
- `finding_label_counts` = гистограмма по семействам (`{"EMAIL": 2, "PERSON": 1}`),
  построенная `_label_counts` по различным плейсхолдерам, так что
  `sum(values) == redaction_count`.
- `placeholder_list` = различные токены-плейсхолдеры, `sorted(...)` — только
  строки-токены, **никогда** оригиналы.

## 5. Интеграция с Langfuse

Два пути кода производят **одинаковую** форму Langfuse:

- **Vector (по умолчанию в проде)** — трансформ `to_langfuse` в
  `helm/.../templates/configmap.yaml`, плюс demo-пайплайн
  `docker/demo-vector/vector.yaml`.
- **Внутрипроцессный `LangfuseSink`** — `audit/langfuse_sink.py`, для тестов,
  низкого объёма или debug-подов, которые отказываются от Vector.

Каждая аудит-запись отображается в **одно `trace-create` + одно
`generation-create`** событие, отправляемое POST на
`{base}/api/public/ingestion` (сверено с `langfuse_sink.py` `_records_to_batch` и
трансформом в configmap):

**Тело `trace-create`**

| Поле | Значение |
|---|---|
| `id` | `request_id` |
| `name` | `corp-llm-gateway` (внутрипроцессный sink) / `gateway-request` (demo Vector) |
| `userId` | `user_id` |
| `metadata` | `team_id`, `redaction_count`, `cache_a_hit`, `finding_label_counts`, `gateway_version`, `status`, `error_code` |
| `tags` | `["team:<team_id>", "provider:<provider>"]` |

**Тело `generation-create`**

| Поле | Значение |
|---|---|
| `model` | `model` |
| `usage` | `{input: prompt_token_count, output: completion_token_count, total: input+output, unit: "TOKENS"}` |
| `metadata` | `latency_ms`, `corp_llm_latency_ms`, `pre_pass_latency_ms` |

**Аутентификация и транспорт**

- HTTP **Basic**-аутентификация: `LANGFUSE_PUBLIC_KEY` : `LANGFUSE_SECRET_KEY`
  (`base64(public:secret)` в Python-sink; Vector `auth.strategy: basic` с теми же
  env-переменными).
- `POST {base}/api/public/ingestion`, `Content-Type: application/json`.
- Буфер (prod Vector langfuse sink): **диск, 1 GiB** (`max_size:
  1073741824`).

**КРИТИЧЕСКИЙ момент дизайна — только metadata, без контента.** Trace в Langfuse
хранит **только metadata**; текст промпта или ответа не отправляется. Тела
`trace-create`/`generation-create` несут счётчики токенов, латентности,
статистику редактирования и лейблы плейсхолдеров — никогда текст сообщений. Как
следствие, панели **Input / Output** трейса намеренно **ПУСТЫ**. В
аудит-хранилище нет оригиналов.

> Замечание по реализации: demo-пайплайн Vector устанавливает `metadata` трейса в
> целую аудит-запись (`metadata: audit`), что всё равно исключает оригиналы,
> потому что сама аудит-запись их никогда не содержит (NEVER-гейт).
> Внутрипроцессный sink и prod-configmap используют курируемое подмножество
> metadata выше.

**Чтение трейсов для безопасности.** Фильтруйте по тегу `team:<id>` /
`provider:<p>`; смотрите `redaction_count` + `finding_label_counts` +
`placeholder_list`. Помните: **пробный запрос закономерно показывает
`redaction_count = 0`** — отсутствие редактирований не есть отсутствие
активности.

## 6. Интеграция с SIEM

Гейт NEVER-полей существует в **двух** местах — внутрипроцессный
`assert_no_never_fields` (`audit/invariants.py`) и Vector VRL-фильтр (prod
`enforce_audit_schema`; demo `never_fields_gate`) — **эшелонированная защита**.
Запись, содержащая любой NEVER-ключ, **отбрасывается**; согласно плану M3-3 это
инкрементирует метрику `audit_drop`, которая **должна поднимать SIEM-алерт**
(M3-9).

Что SIEM должен мониторить (согласно плану M3-9):

| Сигнал | Значение |
|---|---|
| `audit_drop > 0` | NEVER-поле достигло аудит-конвейера — попытка утечки/регрессия; расследовать немедленно |
| Fail-closed `503`-и | `E_CORP_LLM_DOWN`, `E_REDIS_DOWN`, fail-closed S3/буфера Vector и т.д. (доступность + возможная атака) |
| `litellm_pre_call_input_placeholder_literal_detected` | Пользователь ввёл литералы `[LABEL_NNN]` — возможное зондирование санитайзера |
| Аномалии редактирования | Всплеск редактирований (3σ), отказы в обходе, всплески отказов аутентификации |

**NEVER_FIELDS** (точно, из `audit/invariants.py`; сравнение регистронезависимо и
трактует `-` как `_`, поэтому `X-Corp-Auth` / `Set-Cookie` матчатся):

```
mapping, mapping_table, pairs, original_content, unredacted_content,
pre_sanitization, replace_md, rule_values, x_corp_auth, corp_token,
authorization, cookie, set_cookie
```

**Текущий статус (2026-07-01).** Vector SIEM-sink **и** алерты
`AuditVectorDropHigh` / `LeakAttemptDetected` теперь **подключены** (CP-3:
`helm/.../templates/configmap.yaml` siem-sink + `templates/siem-alerts.yaml`,
через тот же VRL-гейт NEVER-полей). Остаётся **единственный** пункт —
подтвердить реальный SIEM-эндпоинт (open question #3); настроенный эндпоинт пока
placeholder. Актуальный статус — в `docs/requirements-compliance.md` (R15).

### 8.1 `vectorBufferFull` в compose-стеке — `continue`, а не значение по умолчанию

Строка матрицы выше не изменена и остаётся источником истины. Эта заметка
фиксирует, где на ней находится один из поставляемых деплоев, потому что раньше
это расхождение было незаметным.

**`compose/` использует опцию `audit_buffer_full=continue` и не может иначе.
Этот стек НЕ обеспечивает поведение fail-closed (503), заданное матрицей по
умолчанию: запросы продолжают уходить наружу, пока доставка аудита стоит.**

Почему не может: `compose/docker-compose.yml` не задаёт `CORP_AUDIT_SINK`,
поэтому применяется `StdoutSink` по умолчанию из `audit/factory.py`, и всё
действие шлюза по аудиту — это одна строка в его собственный stdout, которая
всегда успешна. Vector читает этот лог-файл **вне процесса**, из другого
контейнера. Пути сигнала от состояния буфера Vector обратно в `pre_call` /
`post_call` не существует, поэтому ничто в пути запроса не может увидеть
переполнение и вернуть 503; `when_full: block` лишь останавливает чтение в
Vector. Чтобы закрыть разрыв, нужен health/buffer-гейт в `src/`, питающий хук —
он не реализован.

Остаточный риск и что его ограничивает: пока sink стоит, принятые аудит-записи
живут только в docker json-file логах контейнера `litellm` плюс то, что уже
попало в дисковый буфер Vector. Glob файлового источника Vector покрывает и
активный `-json.log`, и его нумерованные ротации (`-json.log.[0-9]`, а также
двузначная форма), поэтому сама по себе ротация записи больше не теряет — но
файл, вытесненный за пределы `max-file`, docker удаляет, так что **долговечность
аудита здесь по-прежнему ограничивает retention docker-логов, а не дисковый
буфер**. Отдельно: HTTP-sink Vector повторяет только 408/429/5xx, поэтому
неверный или ротированный project-ключ Langfuse (401) приводит к отбрасыванию
записи, а не к буферизации; при этом файловый источник фиксирует чекпоинт по
факту ЧТЕНИЯ, а не доставки, поэтому при перезапуске эти байты повторно не
читаются. Восстановление — удалить чекпоинт источника в `data_dir`; записи,
уже вытесненные ротацией, невосстановимы.

Поэтому операторы этого стека обязаны рассчитать retention docker-логов
(`LITELLM_LOG_MAX_SIZE` × `LITELLM_LOG_MAX_FILE`, задаются в собственном
`logging.options` сервиса `litellm`) на самый долгий допустимый простой Langfuse
и настроить алерты на рост буфера и на ошибки `Events dropped` в Vector. Учтите:
задать их в `log-opts` **демона** не сработает — docker подмешивает log-opts
уровня демона в контейнер только тогда, когда драйвер контейнера совпадает с
драйвером демона по умолчанию, а этот сервис жёстко задаёт `json-file`, потому
что этого требует аудит-пайплайн. Конкретные команды: `compose/README.md`,
раздел "Audit buffering is not fail-closed".

На Helm-деплой эта заметка не распространяется — это отдельная композиция.

### 8.2 Доверие к источнику аудита в compose-стеке — предусловие на хосте

Дополняющая заметка, та же область, что и §8.1: она фиксирует предусловие одного
из поставляемых деплоев и ничего не меняет в матрице выше.

`compose/vector/vector.yaml` читает логи **всех** контейнеров на хосте
(read-only bind `/var/lib/docker/containers` — выбран вместо монтирования
docker-сокета, которое равнозначно root на хосте). Фильтр
`gateway_container_only` ограничивает пайплайн шлюзом, требуя штамп `attrs`
драйвера docker json-file, который порождают метка
`com.corp-llm-gateway.audit-source` сервиса `litellm` вместе с его
`logging.options.labels`.

**Этот фильтр — защита от ошибки конфигурации, а не граница безопасности.** Имя
метки и её значение публичны и никак не проверяются. Любой контейнер, запущенный
на том же хосте с той же меткой и тем же `--log-opt labels=…`, получит такой же
штамп `attrs`; и если он напечатает JSON в форме `AuditEvent` (`request_id` +
`redaction_count`, без NEVER-полей), строка пройдёт `gateway_container_only`,
NEVER-гейт и `audit_only` и попадёт в Langfuse как настоящая аудит-запись.
Фильтр поднимает планку с «может писать строку в лог» до «может запустить
контейнер на этом хосте» — это реальное улучшение, и это всё.

Что нужно принять до деплоя этого стека:

- **Никаких недоверенных `docker run` на этом хосте.** Членство в группе
  `docker`, а также любой CI-раннер, агент или sidecar с доступом к демону
  равнозначны праву записи в аудит-след. Ограничивайте их так же, как сам
  аудит-стор.
- Экспозиция — это **подделка (вставка), а не раскрытие**. Ничто здесь не даёт
  соседнему контейнеру читать аудит-записи шлюза; инвариант #1 и NEVER-гейт не
  затронуты: поддельная запись всё равно не пронесёт NEVER-поле, а оригиналы
  по-прежнему не попадают ни на одну из этих поверхностей.
- Закрыть это по-настоящему может только **приватный канал**, в который пишет
  лишь шлюз, — выделенный bind-mount файл аудита или unix-сокет вместо stdout
  контейнера. Это изменение аудит-sink в `src/corp_llm_gateway/audit/` плюс
  источника Vector, а не compose-стека; оно не реализовано.

На Helm-деплой это не распространяется: там путь аудита — лог самого пода,
ограниченный сборщиком логов k8s, и действует другая модель доверия.

## 10. Форензик-следы (расследование инцидента)

Куда смотреть в первую очередь и что каждый след может и не может рассказать:

| След | О чём говорит | Никогда не содержит |
|---|---|---|
| `finding_label_counts` | Какие ВИДЫ секретов были отредактированы (гистограмма по семействам) | Любой текст |
| `placeholder_list` | КАКИЕ токены были выпущены (`[EMAIL_001]`, …) | Оригиналы |
| `redaction_count` | Сколько РАЗЛИЧНЫХ секретов | — |
| `litellm_pre_call_input_placeholder_literal_detected` (лог) | Пользователь ввёл литералы `[LABEL_NNN]` — возможное зондирование; **не содержит контента** (только счётчик) | Текст литерала |
| Логи жизненного цикла pre/post (`litellm_pre_call_*`, `litellm_post_call_*`, `litellm_audit_emitted`) | Поток на запрос, размеры в байтах, суммарные редактирования, латентности | Тела контента |
| Логи границы ответа (`gateway_desanitize_*`, `gateway_terminal_audit_*`) | Ответ, который не удалось восстановить (фаза + тип исключения), итоговая запись, которая не записалась, повторилась или потерялась | Контент, сообщения исключений |

Маркеры отложенных пробелов в коде (ищите их, чтобы подтвердить, что поведение —
известный пробел, а не регрессия): комментарии `SECURITY` в
`sanitizer/content_blocks.py` (потоковая де-санитизация tool_use,
thinking/redacted_thinking, бинарные/url источники document) и заметка памяти
`project_tool_use_input_unsanitized`.

**Во время инцидента:** начинайте с долговременного хранилища S3 (по командам,
партиционировано по дате) и Langfuse (фильтр по тегу `team:`/`provider:`).
Убедитесь, что `audit_drop` равен нулю — ненулевое значение означает, что
NEVER-поле достигло конвейера, и это первое, за чем гнаться. Ни одна из этих
поверхностей не может содержать оригинал по построению; если кажется, что
содержит, — это регрессия M1-14.

## 13. Мосты подписочной аутентификации

Два опциональных флага позволяют разработчику оплачивать вызов апстрима своим
собственным подписочным OAuth-токеном вместо общего API-ключа, так что ни на
ноутбуке, ни в кластере не лежит ключ провайдера:

| Флаг | Апстрим | Принимаемый токен |
|---|---|---|
| `CORP_LLM_FORWARD_CHATGPT_AUTH` | ChatGPT Codex (OpenAI Responses) | OAuth-bearer Codex |
| `CORP_LLM_FORWARD_ANTHROPIC_AUTH` | Anthropic | **только** токены `sk-ant-oat…` |

Оба читают один и тот же входящий bearer из `Authorization`, поэтому **включён
может быть ровно один**. Оба флага сразу — отказ на старте в
`build_guardrail()` и в `gateway-admin config check`
(`settings.forward_auth_conflict`). Несущая проверка — именно рантайм-овая:
compose- и demo-загрузки, на которых эти мосты и ездят, никогда не вызывают
`settings.validate()`. Установленный `LITELLM_MASTER_KEY` отвергается так же,
пока включён любой из мостов: с master key litellm читает входящий
`Authorization` как один из своих virtual key и отвечает 401 ещё до `pre_call`,
так что мост никогда не увидит токен. Считается **наличие**, а не
«истинность»: пустой `LITELLM_MASTER_KEY=` для litellm тоже «установлен».

Дальше — про мост Anthropic (`litellm_hook.py`, `_anthropic_upstream_headers`
плюс ветка `forward_anthropic_auth` в `pre_call`). Операторская настройка —
[`ops/configuration.md`](ops/configuration.md) и
[`ops/install.md`](ops/install.md).

### Что пробрасывается, а что нет

Для запроса, чей алиас модели резолвится в провайдера `anthropic`, и только при
включённом флаге, `pre_call`:

- копирует значение bearer-а в `data["api_key"]`. Именно это выбирает
  собственную OAuth-ветку litellm, которая отправляет наверх
  `Authorization: Bearer <token>`, добавляет `oauth-2025-04-20` в
  `anthropic-beta` и `anthropic-dangerous-direct-browser-access: true`, а
  `x-api-key` подавляет;
- копирует разрешённые **не-аутентификационные** входящие заголовки в
  `data["extra_headers"]`. Allowlist — ровно `anthropic-beta`,
  `anthropic-version`, `user-agent` (плюс `authorization`, который выбирается
  для валидации, а затем исключается из `extra_headers`). Все остальные
  входящие заголовки отбрасываются;
- **никогда** не выбирает `X-Corp-Auth` — корп-токен пропускается ещё до
  проверки по allowlist, вдобавок к обычному пути `strip_corp_token`
  (инвариант 4);
- удаляет `data["metadata"]` и верхнеуровневый `data["user"]`, а также те же
  два ключа из собственной копии запроса litellm в `model_call_details`
  (см. ниже).

Отвергается: отсутствующий `Authorization`, схема не `Bearer`, пустой bearer,
bearer с CR или LF и любой токен, не начинающийся с
`ANTHROPIC_OAUTH_TOKEN_PREFIX` литэллма (`sk-ant-oat`) — включая обычный
API-ключ `sk-ant-api…`. Каждый случай — `401 E_PROVIDER_AUTH` с записью аудита
(`status="failed"`) и `gateway_failure{component="auth"}`, причём отвергнутый
credential не попадает ни в тело ошибки, ни в трейс исключения, ни в метку
метрики, ни в запись аудита, ни в строку лога
(`tests/invariants/test_no_originals_leak.py`).

API-ключи отвергаются намеренно, а не для простоты. На не-OAuth-ветке litellm
добавляет `x-api-key`, тогда как входящий `Authorization` всё ещё домешивается,
и исходящий запрос нёс бы две конкурирующие схемы аутентификации. BYOK на
обычном API-ключе через этот мост — отдельное решение, которое не принималось.

### Инвариант 3 на этом маршруте

Инвариант 3 (проброс BYOK `Authorization`) держится без изменений: входящий
заголовок `Authorization` остаётся во всех наборах заголовков ровно таким,
каким пришёл, а мост его только *читает*. Исходящий заголовок `Authorization`,
который litellm собирает из `api_key`, — **единственный разрешённый пункт
назначения** токена; появление токена где-либо ещё (в другом заголовке, в теле
запроса, в списке моделей роутера, в логе прокси) — это утечка.

Правило закреплено по обе стороны границы процесса, потому что ни один стенд не
видит обе:

| Поверхность | Чем закреплено |
|---|---|
| Эмиссии логгера, тела ошибок, трейсы исключений, метки метрик, записи аудита, наборы пробрасываемых заголовков | `tests/invariants/test_no_originals_leak.py` (внутрипроцессно) |
| Заголовки и тело исходящего запроса, удержанные деплойменты роутера, stdout/stderr самого процесса litellm | `tests/integration/test_anthropic_oauth_outbound.py` (запускает запиненный образ litellm против перехватывающего апстрима) |

Все проверки capture-набора зависят от docker, запиненного образа и
доступности хоста из контейнера, поэтому на машине без них набор пропускается.
CI выставляет `CORP_REQUIRE_PROXY_CAPTURE=1`, и каждый такой пропуск становится
падением — иначе сбой демона, реестра или сети даёт зелёную сборку, не
проверившую ничего. Набор сам сверяет эту проводку с
`.github/workflows/ci.yml`, так что потеря переменной роняет прогон, а не
заглушает его.

### Гейт по провайдеру — эшелонирование, а не гарантия маршрутизации

Мост срабатывает только при `_detect_provider(data) == "anthropic"`. Эта
проверка читает **видимый клиенту алиас модели** (`data["model"]`) и больше
ничего. Реальный деплоймент litellm выбирает *после* pre-call-хука, а
`model_name` в litellm может маппиться на любой `litellm_params.model` — так что
в конфиге с catch-all `model_name: "*"` алиас `claude-…` пройдёт гейт и всё
равно может уехать на не-Anthropic-апстрим вместе с подписочным токеном.

Значит, гейт — это дешёвая вторая линия защиты от копирования токена в вызов
OpenAI или корп-vLLM. **Несущий контроль — форма деплоймента**: конфиг litellm,
в котором все маршруты — `anthropic/` и нет wildcard-а.
`docker/anthropic-oauth/litellm-config.yaml` — именно такой конфиг, а
`tests/test_anthropic_oauth_profile.py` закрепляет оба свойства. Не читайте
гейт как гарантию, которую он дать не может.

### Зачистка `metadata` / `user`

Шлюз санитизирует `messages`, `system` и `instructions`. Он никогда не
санитизирует `metadata` и верхнеуровневый `user`, а оба уезжают в Anthropic:

- на **chat-completions-адаптере** litellm маппит верхнеуровневую строку `user`
  в `metadata.user_id` и копирует `metadata.user_id` в исходящее тело. Его
  единственный фильтр отвергает лишь полные формы email и телефона;
- на **pass-through-маршруте `/v1/messages`** — том самом, который использует
  Claude Code, — `metadata` отсутствует в декларативном списке
  «поддерживаемых» параметров, но *ничто не фильтрует запрос по этому списку*,
  так что переданный вызывающей стороной `metadata` уходит наверх целиком.

Поэтому зачистка несущая на **обоих** маршрутах. Мост гейтится по провайдеру, а
не по типу вызова, так что при включённом флаге достижимы оба.
`tests/litellm_hook/test_litellm_route_assumptions.py` закрепляет оба поведения
litellm, а удаление зачистки красит capture-тесты в красный с видимой канарейкой
в исходящем теле.

**Удаление, а не санитизация.** Прокси litellm набивает `data["metadata"]`
десятками внутренних учётных ключей разных типов, так что сужать не до чего;
санитизация чеканила бы плейсхолдеры в полях, которые обратный путь никогда не
разворачивает, оставляя пары, которые никто не потребляет; а зачистка по
конкретному ключу тихо открыла бы дыру в тот день, когда litellm начнёт
копировать в тело ещё один ключ metadata. Цена — потеря собственных учётных
метаданных litellm на этом маршруте; это приемлемо, потому что маршрут едет без
virtual key и, значит, без учёта расходов в любом случае. Атрибуция аудита не
страдает: `user_id` / `team_id` приходят из `AuthMiddleware`, а `request_id`
ключуется на `litellm_call_id`.

### Исключение для identity-преамбулы

OAuth-аутентифицированный маршрут Anthropic признаёт запрос запросом Claude Code
по ведущему блоку `system`, сопоставляя его **точным равенством строк** с тремя
фиксированными литералами клиента (`sanitizer/identity_preamble.py`). Один
отредактированный символ — и это уже не тот блок; а с боевым набором детекторов
spaCy размечает `Claude` как PERSON и `CLI` как ORG, так что санитайзер
действительно переписывал преамбулу, пока этого исключения не было.

Исключение намеренно узкое. Оно применяется **только** когда:

- `CORP_LLM_FORWARD_ANTHROPIC_AUTH` включён **и** запрос резолвится в провайдера
  Anthropic — вне моста литерал identity является обычным контентом;
- поле — `system`. Никогда `instructions`, пользовательское сообщение,
  `tool_result` или `document`: операторское правило `replace.md` или запись
  газеттира обязаны по-прежнему уметь отредактировать ту же строку в этих
  местах;
- блок — **ведущий**. Перед ним допустимы только блоки
  `x-anthropic-billing-header:` (litellm сохраняет их на first-party-маршруте
  Anthropic, поэтому реальная нагрузка может прийти с identity-блоком на
  индексе 1). Более позднее вхождение, после любого обычного блока промпта,
  санитизируется как любой другой лист;
- совпадение **побайтовое**. Никакого `strip()`, никакой терпимости к пробелам:
  дополненное значение всё равно не пройдёт наверху, а терпимость позволила бы
  провезти неограниченный текст в непроверенный лист.

Дырой это не является по двум причинам. Освобождённые строки — фиксированные
константы клиента, никогда не пользовательский контент, так что их освобождение
не может утечь оригинал (M1-14). И освобождение действует **только на
перезапись**: блок по-прежнему собирается `collect_text`, поэтому классификатор
payload-ов Stage 0 и DLP-страж egress-а Stage 5 читают его ровно как раньше, а
fail-closed-проверка размера выполняется до того, как исключение может
примениться. Это тот же раскол «перезапись против скана», который уже применяется
к полям `signature` в блоках.

Соседние блоки `system` не затронуты, включая billing-маркеры перед
identity-блоком: они идут через обходчик **целиком**, вместе с текстом маркера.
В более ранней версии фиксированный префикс `x-anthropic-billing-header:`
удерживался и приклеивался обратно после санитизации остатка. Правила
`replace.md` — это буквальный поиск подстроки в переданном оркестратору тексте,
поэтому такой раскол скрывал любое правило, чей шаблон заходил за границу
«префикс/остаток», а затем восстанавливал полный оригинал по пути в Anthropic —
нарушение M1-14, которое Stage 5 не ловит, так как он не проигрывает
`replace.md`. Теперь ничего не приклеивается обратно. Если правило переписало
маркер, identity-блок перестаёт быть *ведущим* и Anthropic может отклонить
запрос: отклонённый запрос — это цена UX, восстановленный оригинал — это утечка.
`tests/sanitizer/test_oauth_system_preamble.py` гоняет реальный `pre_call` с
боевыми детекторами, включая правило, пересекающее эту границу, а capture-тест
проверяет, что редактируемый email в соседнем блоке всё так же возвращается как
`[EMAIL_nnn]` — так что побайтовые проверки не могут тихо стать
бессодержательными.

### Удержание credential-ов в процессе litellm

litellm считает любой запрос с `api_key` носителем clientside credential:
`_handle_clientside_credential` строит `Deployment`, id которого хеширует
динамические параметры, и делает upsert в `Router.model_list` — **вместе с
сырым ключом**. Ничто его не вытесняет. Каждое отдельное значение
`sk-ant-oat…` поэтому оставляет один деплоймент с credential-ом, живущий всё
время жизни процесса прокси; повторное использование токена не добавляет
ничего. Это измерено, а не предположено —
`test_each_distinct_token_retains_exactly_one_router_deployment`.

Это **не привнесено мостом Anthropic** — у моста ChatGPT Codex ровно та же
форма с момента его появления, — но этот маршрут добавляет второе место, где
так происходит, так что в памяти накапливается больше разных credential-ов
разработчиков. Границы и меры:

- админ-поверхность их не отдаёт: `/model/info` не возвращает ни один из
  токенов;
- токены не попадают в stdout/stderr процесса (закреплено capture-тестом) и ни
  в одну поверхность аудита;
- **мера — перезапуск процесса litellm.** Ручки вытеснения нет. Считайте время
  жизни процесса окном удержания, оценивая, как долго скомпрометированный
  подписочный токен остаётся в памяти.

### Топология

Подписочная аутентификация — production-режим. Она работает на production
compose-стеке с override-ом `docker-compose.oauth.yml` и на демо-оверлее
`anthropic-oauth` (`docker-compose.demo.yml` + `docker-compose.anthropic-oauth.yml`).

| Развёртывание | Статус | Почему |
|---|---|---|
| Production compose + `docker-compose.oauth.yml` | **Поддерживается** | Только Anthropic-маршруты, нет wildcard-а, нет `LITELLM_MASTER_KEY`, поэтому входящий bearer доходит до `pre_call` |
| Демо-оверлей `anthropic-oauth` | **Поддерживается (демо)** | Та же форма поверх демо-стека |
| Helm-чарт | **Не поддерживается** | Его litellm-ConfigMap маршрутизирует `"*"` в корп-vLLM и не имеет маршрута `anthropic/`, так что OAuth-ветка litellm недостижима — а этот wildcard как раз та форма, от которой алиасный гейт не защищает |

**Следствие, которое принимается сознательно:** виртуальных ключей litellm нет,
а значит нет и нативного контроля бюджетов, rate limit-ов и квот. Это решение, а
не пробел в ожидании раскладки заголовков: management-контур litellm, включая
`/key/*`, отклоняется на route gate (§14), так что выпустить
виртуальный ключ нечем. Режим API-ключей остался только тестовой позой.

## 14. Route gate

`CorpLlmGuardrail` — это **callback** litellm, и litellm вызывает его только из
тех хендлеров, которые идут через его общий обработчик запросов. Хендлеры в
закреплённой версии litellm (1.101.0), которые через него не идут, — три
подтверждённых обхода и все прочие хендлеры без хука, которые таблица
отклоняет, — доходили до провайдера **без проверки `X-Corp-Auth`, без
санитизации, без DLP-скана Stage 5 и без аудит-записи**. Ещё один класс доходил
до хука, но никогда не переписывался, потому что хук читает только `messages` и
`input`. Все они перечислены в §2. Route gate закрывает этот класс дыр
окончательно: что бы ни делали роутеры litellm, запрос теперь должен быть
классифицирован до того, как какой-либо из них сможет на него ответить.

### Где он работает

`src/corp_llm_gateway/asgi.py` — единственная поддерживаемая точка запуска
(`python -m corp_llm_gateway.serve`, ENTRYPOINT образа). Он оборачивает
ASGI-приложение litellm — именно оборачивает, а не через `add_middleware`, —
поэтому `RouteGateMiddleware` **самый внешний**: любой middleware, который
добавляет litellm, находится внутри него, и ни один не может ответить раньше
гейта. CLI `litellm` и `litellm.proxy.proxy_server:app` больше никогда не должны
быть точкой запуска: оба отдают роутеры, перед которыми ничего не стоит.

На compose-стеке опциональный HTTPS-фронт (`compose/nginx/`) стоит снаружи
образа, поэтому запрос проходит эти слои, начиная с самого внешнего:

```
nginx-фронт         compose, COMPOSE_PROFILES=nginx|nginx-ports, по умолчанию выключен:
                    TLS (или доверенный терминатор), allow-list по точным путям → 404,
                    лимиты на токен на периметре → 429 E_RATE_LIMITED
   ↓
RouteGateMiddleware классификация (METHOD, path) → PASSTHROUGH / REWRITTEN / REFUSE
   ↓
лимитер в полёте    только REWRITTEN: тело дочитано (не UTF-8 JSON → 415, ключ
                    `policies` верхнего уровня → 403), затем слот → 429 E_CAPACITY
   ↓
десанитайзер        обратная подстановка ответа, на выходе (ниже)
   ↓
роутер litellm      pre_call_hook → санитизация → провайдер
```

Без профиля, как и в Helm, самый внешний слой — route gate.

**Обратная подстановка ответа выполняется здесь, а не в litellm.**
`DesanitizeMiddleware` (`route_gate/desanitize_middleware.py`) стоит внутри
лимитера, перед приложением litellm, и это единственная обратная подстановка
шлюза: pre-call guardrail передаёт маппинг ответа тикету запроса, а middleware
восстанавливает оригиналы в ответе, который отправляет litellm, поэтому litellm
и все callback-и, хуки и логи внутри него видят только плейсхолдеры. Выключателя
нет. Единственная аудит-запись запроса пишется, когда ответ заканчивается, и
никогда — callback-ом litellm. Её контракты — корреляция, состояние, граница
исключений, форматы, итоговая запись — в §15.

Middleware написан на чистом ASGI, а не на `BaseHTTPMiddleware`, по двум
причинам, важным для безопасности: он должен видеть scope-ы `websocket` (HTTP
middleware их никогда не видит, так что рукопожатие прошло бы
неклассифицированным), и он не должен буферизовать — SSE-стриминг должен
проходить нетронутым.

### Таблица генерируется, а не пишется руками

`route_gate/table.py` перегенерируется из исходников самого litellm
`ast`-коллектором (`tests/route_gate/litellm_routes.py`), а
`tests/route_gate/test_litellm_route_guard.py` на каждом прогоне CI заново
запускает этот коллектор против установленного litellm. У маршрута, который
litellm добавит при следующем обновлении, записи нет, поэтому guard падает, пока
кто-то его не классифицирует, — а в рантайме он тем временем отклоняется по
default-deny. Маршрут `POST`/`PUT`/`PATCH` без хука может быть PASSTHROUGH только с
письменным обоснованием, и guard сверяет это обоснование с `ast`: хендлер, тело
которого вызывает `litellm.acompletion`, `aresponses`, `token_counter`,
`router.a*` или `pass_through_request`, комментарием не оправдать.

### Как выглядит отказ

| Причина | Статус | Код ошибки | Когда |
|---|---|---|---|
| `route_gate_listed` | 403 | `E_ROUTE_BLOCKED` | таблица отклоняет эту пару `(method, path)` |
| `route_gate_unlisted` | 404 | `E_ROUTE_BLOCKED` | записи в таблице нет — default-deny |
| `route_gate_websocket` | 403 | `E_ROUTE_BLOCKED` | scope websocket или заголовок `Upgrade: websocket`, на любом пути |
| `route_gate_malformed` | 403 | `E_ROUTE_BLOCKED` | сырой путь содержит `%2f`, `%00`, `%2e%2e` (в любом регистре) или не-ASCII байт, либо декодированный путь содержит `..`, `//` или NUL (`route_gate/classify.py`); с таблицей вообще не сверяется |
| `route_gate_unarmed` | 503 | `E_ROUTE_GATE_UNARMED` | REWRITTEN-маршрут, пока guardrail-callback не зарегистрирован; никогда не пробрасывается |
| `route_gate_error` | 500 | `E_ROUTE_GATE_ERROR` | классификация бросила исключение; никогда не пробрасывается |
| `route_gate_body_policies` | 403 | `E_ROUTE_BLOCKED` | допущенный REWRITTEN-запрос, в JSON-теле которого есть ключ `policies` верхнего уровня (litellm применил бы эти политики к запросу); проверяется, когда лимитер дочитал тело, до слота и до разбора тела litellm |
| `route_gate_body_not_json` | 415 | `E_ROUTE_BLOCKED` | допущенный REWRITTEN-запрос, чьё тело не UTF-8 JSON: тип носителя не `application/json` (или непустое тело без `Content-Type`), `charset` не `utf-8` (`utf8` — то же самое; повторённый или некорректный отклоняется) или тело, кодировку которого `json.detect_encoding` определяет не как `utf-8` (BOM, UTF-16, UTF-32), либо которое не декодируется как UTF-8. litellm прочитал бы тело формы, включая поле `policies`; а проверка `route_gate_body_policies` читает байты: только для UTF-8 «нет ASCII `policies` и нет `\u`» доказывает отсутствие ключа (тело в UTF-16 записывает его байтами, которые проверка не находит, а стандартный `json.loads(bytes)` его декодирует). Проверяется на том же дочитанном теле; `tests/route_gate/test_body_policies.py::test_a_body_that_is_not_utf8_is_refused_before_litellm_or_a_slot`, `::test_a_charset_other_than_utf8_is_refused_before_litellm_or_a_slot`, `::test_no_encoding_stdlib_json_decodes_carries_a_policies_key_past_the_gate` |

`route_gate_unarmed` и `route_gate_error` также пишут `gateway_failure{component="route_gate"}`. Каждый
отказ пишет `corp_llm_gateway_blocked_requests_total{block_reason=…}` и эмитит
аудит-запись с причиной и кодом ошибки — только ALWAYS-поля, потому что гейт
отклоняет запрос до того, как определена какая-либо идентичность.

**Отказ никогда не читает тело запроса** и никогда его не возвращает. Ответ
называет только тот маршрут, который прислал сам клиент. Строка лога содержит
причину, тип scope и метод, суженный до известных глаголов, — ни пути, ни
заголовков, ни текста исключения (поверхности M1-14 ii, iii, vi;
`tests/invariants/test_no_originals_leak.py`).

### Старт: шлюз не работает в полусконфигурированном виде

Собственный lifespan litellm молча пропускает отсутствующий файл конфига и
запускает прокси **вообще без guardrail-callback** — это и есть fail-open,
который гейт должен закрыть. Точка входа отказывает раньше: exit 78
(`EX_CONFIG`), когда конфиг litellm отсутствует, не читается, не является YAML
или настраивает `pass_through_endpoints` либо `general_settings.database_url`, а
также когда `CORP_LLM_ROUTE_GATE_EXTRA_PASSTHROUGH` некорректен или называет
отклонённый маршрут, или когда тестовый `CORP_LLM_ALLOW_LITELLM_DEBUG` задан при
`CORP_ENV=prod|production`; exit 70 (`EX_SOFTWARE`), когда старт litellm
завершился без `CorpLlmGuardrail` в `litellm.callbacks`, с guardrail, настроенным
так, что litellm его обойдёт, с включённым DEBUG litellm или с компрессором ответов
в приложении litellm — по строке `arm refused (<problem>)` на каждую проблему,
все перечислены в §15. Пока эта проверка не пройдена, гейт
**не взведён** (unarmed), и невзведённый гейт отвечает 503 на каждом
переписываемом маршруте вместо того, чтобы пробросить запрос.

### Маршрут выдачи токенов: принадлежит шлюзу, завершается локально, ограничен

`POST /internal/issue-token` — единственная строка с методом с телом в
`GATEWAY_ROUTE_TABLE`. Она PASSTHROUGH, чтобы гейт передал запрос собственному
`HealthRouter` шлюза, который отвечает на него сам и никогда не пробрасывает в
litellm. При выключенной выдаче (`CORP_GATEWAY_ISSUE_OIDC_ISSUER` не задан) это
локальный 404 `E_ISSUE_DISABLED` для любого метода. Слот лимита
одновременных запросов он не занимает никогда. При включённой выдаче он
ограничен, как любой публичный эндпоинт, в таком порядке:

1. **Лимиты маршрута, до любой работы.** Свой лимит одновременных запросов
   (`CORP_GATEWAY_ISSUE_MAX_INFLIGHT`, по умолчанию 4) и свой token bucket
   (`CORP_GATEWAY_ISSUE_RATE_PER_MINUTE`, по умолчанию 30); они отвечают 429
   `E_ISSUE_INFLIGHT` и 429 `E_ISSUE_THROTTLED` без очереди, а запрос,
   отклонённый первым, не тратит токен bucket-а.
2. **Без тела.** Access-токен Keycloak берётся только из заголовка
   `Authorization: Bearer`. Любой байт тела отклоняется (400 `E_ISSUE_BODY`);
   чтение останавливается на 1 KiB и на 2 с (408 `E_ISSUE_BODY_TIMEOUT`).
3. **JWT.** Только RS256; обязательны `exp`, `iat`, `iss`, `aud`, `sub`, `jti` и
   `azp`; `aud` должен содержать `CORP_GATEWAY_ISSUE_OIDC_AUDIENCE` и не должен
   содержать операторскую аудиторию `CORP_GATEWAY_OIDC_AUDIENCE` (они обязаны
   различаться — иначе отказывают config check и старт); `azp` должен
   совпадать с `CORP_GATEWAY_ISSUE_OIDC_CLIENT_ID`. JWKS загружается по HTTPS
   (в prod), без редиректов, за 3 с, не больше 64 KiB, одной общей загрузкой на
   всех ждущих, с проверкой по `CORP_LLM_CA_BUNDLE`, если он задан. Ошибка —
   401 `E_OIDC_*`; недоступный JWKS — 503 `E_JWKS_UNAVAILABLE`.
4. **Команда.** Команду задаёт первая группа из
   `CORP_GATEWAY_ISSUE_OIDC_TEAM_MAP` (в порядке карты), в которой состоит
   пользователь; нет такой — 403 `E_ISSUE_NO_TEAM`; команда из карты, которой
   нет в хранилище, — 403 `E_ISSUE_UNKNOWN_TEAM`: шлюз никогда не создаёт
   команду по claim-ам.
5. **Политика выпуска по `(iss, sub)` в одной транзакции Postgres** под
   advisory lock уровня транзакции (так что сериализуются реплики, а не только
   один процесс): уже использованный `jti` — 403 `E_ISSUE_REPLAY` (страховка —
   уникальный индекс); повторная выдача раньше
   `CORP_GATEWAY_ISSUE_MIN_INTERVAL_SECONDS` — 403 `E_ISSUE_RATE` (отозванные и
   истёкшие строки считаются, поэтому отзыв интервал не сбрасывает); сверх
   `CORP_GATEWAY_ISSUE_MAX_ACTIVE` живых токенов самые старые отзываются.
   Транзакция идёт с `lock_timeout` 5 с и `statement_timeout` 8 с; срабатывание
   любого — 503 `E_ISSUE_BUSY`.
6. **Одна граница на шаги 3-5**: `CORP_GATEWAY_ISSUE_STORE_TIMEOUT_SECONDS`
   (по умолчанию 10, 5-300). До шага 3 схема токенов, ещё не признанная
   актуальной («Старт», ниже), — 503 `E_ISSUE_SCHEMA`. После границы запрос
   отвечает 503 `E_ISSUE_STORE_TIMEOUT` и освобождает свой слот; сбой хранилища класса
   «соединение» — 503 `E_ISSUE_STORE_UNAVAILABLE`; всё прочее — 500
   `E_ISSUE_INTERNAL`. Отменённый запрос к базе получает серверную отмену в
   пределах 0,5 с, затем его соединение закрывается (`pg_session.py`).

Успех — 200 `{"corp_token", "expires_at"}`. Каждый ответ выдачи несёт
`cache-control: no-store`. Тела ошибок несут только код, а единственная строка
лога на запрос — статус и код; никогда bearer, выданный токен, `sub`, группы или
имя пользователя (`tests/invariants/test_issuance_no_leak.py`; набор кодов
закреплён `tests/invariants/test_issuance_error_codes.py`).

**Старт.** Выдаче нужен Postgres. Точка входа завершается с кодом 78, если
выдача включена без `CORP_LLM_PG_DSN`, сконфигурирована частично, без extra
`oidc` или `postgres`, с нечитаемым `CORP_LLM_CA_BUNDLE`, или если Postgres
отвергает DSN (учётные данные, имя базы, синтаксис), TLS-рукопожатие (в том
числе `sslmode=require|verify-*` в DSN, от которого сервер отказался) или право
читать `corp_tokens`, а также если в `corp_tokens` нет issuance-колонок или
валидного уникального индекса `corp_tokens_oidc_jti_key` только по `oidc_jti`.
Postgres, недоступный по сети (08xxx, 57P0x, 53300, ошибка сокета), даёт
предупреждение, и шлюз стартует (`pg_session.BOOT_PROBE_OUTCOMES`) с
непроверенной схемой: пока повторная проверка не увидит её актуальной,
`/healthz/ready` отвечает 503, а маршрут — 503 `E_ISSUE_SCHEMA`. Readiness и сам
маршрут повторяют ту же проверку схемы с общим ограничителем — не больше одного
запроса в 15 с на обоих, через пул самого хранилища токенов — и прекращают после
успеха (`healthz/checks.py` `IssuanceSchemaGate`), поэтому развёртывание, чей
healthcheck опрашивает только `/healthz/live` (compose), всё равно
восстанавливается на следующей попытке выдачи. Detail readiness называет
проблему и способ её устранить, но никогда не DSN. Readiness ходит в Postgres так же, как хранилища, — через пул
хранилища токенов, а до его создания одним соединением с теми же keepalive
startup-параметрами, — поэтому PgBouncer, отвергающий их, выводит pod из
готовности (`postgres_error:StartupParameterRejectedError`).

**Путь аутентификации в рантайме тоже ограничен.** Каждый переписываемый запрос
ищет свой токен `X-Corp-Auth` в том же хранилище: один поиск на токен
одновременно (single-flight, запущенный вне запроса, чтобы отключение одного
клиента не отменило его для остальных), граница запроса 5 с и общая 6 с.
Хранилище, которое не может ответить, — 503 `E_STORE_UNAVAILABLE` с
`gateway_failure{component="token_store"}`, но никогда не пропуск.

### Управляющая поверхность запрещена

Каждый маршрут litellm, который не является генерацией, списком моделей,
сохранённым ответом по id или одной из трёх проб, отвечает **403
`E_ROUTE_BLOCKED`** (`route_gate_listed`) — отовсюду и в обоих режимах
аутентификации: админский JSON API, аналитика расходов, login / SSO /
приглашения, неаутентифицированный публичный каталог, ассеты UI, `GET /` и
`GET /routes`, lazy warm-up роутера и не-пробные строки `/health/*` — 462 строки
админского семейства плюс 8 health-строк. В litellm 1.101.0 таблицы litellm
содержат 26 PASSTHROUGH / 879 REFUSE / 8 REWRITTEN строк (913), плюс 6
PASSTHROUGH-строк собственной таблицы шлюза (`GATEWAY_ROUTE_TABLE`: пробы
`/healthz/*`, `/metrics` и маршрут выдачи);
`tests/route_gate/test_table.py` закрепляет эти числа и то, что ни одна
допущенная строка не несёт причину из отклонённого семейства.

**Почему отказ, а не ограничение по сети.** Ничего из того, что нужно шлюзу в
рантайме, не живёт в management-контуре litellm. Идентичность — это непрозрачный
токен `X-Corp-Auth` в собственном хранилище шлюза: он выдаётся через
`POST /internal/issue-token` по логину в Keycloak и отзывается командой
`gateway-admin token revoke`. Наблюдаемость — это аудит-конвейер в Langfuse.
Поверхность добавила бы лишь способ изменить поведение санитайзера после
старта. План перехода на guardrail API litellm
(`docs/plans/completed/20260926-litellm-guardrail-api-adoption.md`) нашёл три таких пути,
каждый подтверждён пробой:

- **hazard 9** — `POST /guardrails/apply_guardrail` логирует исходный текст и
  глотает исключения post-call (он уже был REFUSE и остаётся им);
- **hazard 14** — `POST /policies` / `PUT /policies/{id}/status` могут создать
  pipeline с нашим guardrail, который цикл pre-call затем пропускает: ноль
  вызовов санитайзера, оригиналы уходят наружу;
- **hazard 15b** — регистрация второго guardrail под нашим именем
  (`POST /guardrails`, `PUT|PATCH /guardrails/{id}`) заставляет балансировку
  litellm запускать чужой callback вместо нашего.

Сетевое правило (loopback, туннель, allow-list в nginx) оставило бы все три в
одной ошибке конфигурации от эксплуатации. Строка REFUSE действует внутри
образа, на любом пути входа.

**Hazard 14 без HTTP-маршрута.** Таблица закрывает HTTP-путь в реестр политик
litellm. Три точки входа идут мимо маршрутов; у первых двух свой гейт, третья открыта:

- **14a, строка политики в БД litellm.** Поставляемые конфиги litellm закрепляют
  `general_settings.supported_db_objects: ["models"]`, поэтому litellm не
  загружает ни политик, ни guardrail-ов из БД.
- **14b, тело запроса с политиками.** Допущенный переписываемый запрос, чьё тело
  не UTF-8 JSON (тип носителя не `application/json`, charset не `utf-8` или тело,
  кодировку которого `json.detect_encoding` определяет не как `utf-8`), получает
  415 `route_gate_body_not_json`, а JSON-тело с ключом `policies` верхнего
  уровня — 403 `route_gate_body_policies`; оба — когда лимитер дочитал тело и до
  того, как его разберёт litellm (таблица выше). Проверка `policies` читает
  байты, и только для UTF-8 тело без ASCII `policies` и без экранирования `\u`
  доказывает отсутствие ключа. litellm 1.101.0 превращает тело UTF-16/32 с BOM
  (или байты не в UTF-8) в пустое тело, а на остальные отвечает 400, так что
  сегодня утечки там нет; парсер, декодирующий как `json.loads(bytes)`, ключ
  нашёл бы.
- **14c, таблица `LiteLLM_Config` litellm — открыто.** В compose (у litellm есть
  БД и `STORE_MODEL_IN_DB=True`; в Helm у litellm БД нет) строка там может
  добавить callback-и логирования или включить промпты в spend-log;
  `supported_db_objects` её не ограничивает. Такой callback получает только
  плейсхолдеры (§15, «БД litellm»).

Ни один из трёх не главный контроль: guardrail — обычный `CustomLogger`, который
litellm никогда не пропускает из-за политики (§15, hazard 14).

**Health-строки по одной.** Поставляемые пробы используют только собственные
`/healthz/live` и `/healthz/ready` шлюза.

| Маршрут | Вердикт | Почему |
|---|---|---|
| `GET` / `OPTIONS /health/liveliness`, `/health/liveness` | оставлен | Читают флаг остановки и возвращают константу (`_health_endpoints.py:1847-1865`, OPTIONS `:1884-1901`) |
| `GET` / `OPTIONS /health/readiness` | оставлен | Проверено в litellm 1.101.0 (`_health_endpoints.py:1740-1760`): читает флаг остановки и, если у litellm есть база, Prisma-пинг, кешируемый на 15 с и ограниченный 4 с (`:1410-1458`, `:1720-1737`). обращаются к провайдерам).

**Режим API-ключей — только тестовая поза** (решение DRI, 2026-09-27). Его
разработчики держали виртуальный ключ litellm, выпущенный через
`POST /key/generate`; когда `/key/*` отклонён, пути онбординга нет, а выдавать
разработчикам master key нельзя. Production-режим — подписочный. Контейнерный
набор тестов (`tests/integration/test_route_gate_container.py`) сохраняет
покрытие режима API-ключей — exit 70 и route gate — вставляя sha256
синтетического ключа `sk-…` напрямую в `LiteLLM_VerificationToken` litellm:
именно так litellm ищет ключ.

`CORP_LLM_ROUTE_GATE_EXTRA_PASSTHROUGH` не может снова открыть ничего из этого
(см. «Расширение»).

### Лимит одновременных запросов: после вердикта, принадлежит шлюзу

Взведённый REWRITTEN-запрос занимает ещё и слот в лимитере шлюза
(`route_gate/inflight.py`, `CORP_LLM_MAX_INFLIGHT`, по умолчанию 64 на pod) и
держит его весь запрос, включая стрим. PASSTHROUGH-маршруты (пробы, список
моделей, маршрут выдачи) не считаются никогда. Лимит принадлежит шлюзу, потому
что собственный лимит litellm здесь мёртв: litellm 1.101.0 учитывает
`general_settings.global_max_parallel_requests` только в своём legacy-лимитере
(его включает `LEGACY_MULTI_INSTANCE_RATE_LIMITING`), а ни один поставляемый
конфиг не задаёт ни того, ни другого.

**Никакого слота, пока тело не пришло целиком.** Лимитер — единственный
читатель `receive` запроса. Сначала он вычитывает всё тело — до того, как
занят слот, и до любой аутентификации, — и только потом пытается занять слот;
поэтому у тела свои границы:

- оно должно прийти за `CORP_LLM_BODY_READ_SECONDS` (по умолчанию 30): после
  этого 408 `E_BODY_TIMEOUT` (`block_reason` `body_timeout`);
- одновременно тело читают не больше `CORP_LLM_MAX_DRAINING` запросов (по
  умолчанию 4 × лимит): следующий получает 429 `E_CAPACITY` без чтения;
- все буферизованные байты тел — читаемых и удерживаемых для допущенного
  запроса до его конца — делят `CORP_LLM_MAX_DRAINING_BYTES` (по умолчанию
  512 MiB): объявленный `Content-Length` или чанк, который его превысил бы,
  получает 429 `E_CAPACITY` и возвращает то, что держал;
- одно тело больше 25 MiB — `oversize:blocked`, 422.

Поэтому неаутентифицированный клиент, который так и не дослал тело, слот не
держит, а тот, кто дослал его после того, как ушёл последний слот, получает 429
в этот момент. Каждый `E_CAPACITY` несёт `Retry-After: 1` и считается как
`corp_llm_gateway_blocked_requests_total{block_reason="capacity"}`; лимитер
отвечает раньше litellm и санитайзера, и ни один его отказ не разбирает, не
возвращает и не логирует тело.

**Граница отвечает `E_RATE_LIMITED`, шлюз — `E_CAPACITY`.** Когда включён
nginx-фронт (`compose/nginx/`), nginx ограничивает каждый корп-токен до того,
как запрос дойдёт до шлюза (`docs/ops/capacity.ru.md`, «Лимиты на границе»):
сверх лимита токена по частоте, всплеску или числу запросов в полёте он отвечает
429 `{"error":{"code":"E_RATE_LIMITED"}}` с `Retry-After: 1`, и запрос до шлюза не
доходит — ни аудита, ни счётчика здесь. Код говорит, какой слой ответил:
`E_RATE_LIMITED` — один токен превысил свою долю, `E_CAPACITY` — pod заполнен.
Токен — ключ лимитера только в разделяемой памяти nginx; его нет ни в одном поле
access-лога, а собственная строка nginx «limiting requests» пишется на уровне
`error`, ниже уровня `crit` фронта. Собственный ключ получает только значение
в форме корп-токена (`ct_` + 43 url-safe символа); пустой, слишком длинный,
повторённый или некорректный `X-Corp-Auth` считается по адресу клиента: nginx
`limit_conn` не обрезает ключ длиннее 255 байт, а пропускает его без лимита, а
повторённый заголовок склеивается в новый ключ.

**Уровень `crit` — то, что держит токен вне stderr.** Две строки nginx уровня
`error` несут сами байты ключа: у `limit_conn` — `the value of the "…" key is
more than 255 bytes: "<key>"`, у `limit_req` — такая же на 65535 байт. Карта по
форме токена держит любой ключ намного короче обоих порогов, так что сегодня ни
одна не срабатывает; но будущее изменение, ослабившее `error_log /dev/stderr
crit` (в `nginx.conf`) или задавшее `limit_req_log_level` / `limit_conn_log_level`,
превратит следующий длинный ключ в токен в логе контейнера.
`tests/compose/test_nginx_profile.py::test_nginxs_limiting_line_is_below_the_error_log_level`
закрепляет оба условия: `error_log` — `crit`, и ни один конфиг не задаёт `*_log_level`.
Единственный достижимый у лимитов `[crit]`: заполненная зона `corp_conn` пишет
`[crit] ngx_slab_alloc() failed: no memory in limit_conn_zone "corp_conn"` на
каждый отклонённый запрос — без контекста запроса и без ключа, а запрос
получает 429 границы. При 10m для этого нужно порядка 10^5 разных ключей в полёте
одновременно — больше, чем `worker_connections` nginx.

**Отключение завершает запрос.** Лимитер воспроизводит тело для litellm и следит
за сокетом. Клиент, который отключился — во время нашего pre-call-хука, до
первого байта или посреди стрима, — получает отмену запроса, отмену оставшихся
задач, одну аудит-запись `cancelled` только со счётчиками
(`E_CLIENT_DISCONNECTED`) и возврат слота не позже 2 ×
`CORP_LLM_CANCEL_GRACE_SECONDS` (`docs/ops/capacity.md`). Pre-call, до которого
litellm добрался уже после отмены, получает 408 `E_CLIENT_DISCONNECTED` и
второй записи не пишет.

**Общие задачи никогда не принадлежат запросу.** Задача, которую ждут несколько
запросов (поиск токена, загрузка JWKS), запускается вне всех запросов
(`inflight.spawn_shared`), а logging worker litellm стартует в lifespan и не
помечается, поэтому отключение одного клиента не отменяет работу для остальных
и не останавливает последующие аудит-callback-и.

**Лимит — это ёмкость, а не авторизация.** Он решает, сколько запросов идёт, но
никогда — какие: каждый допущенный запрос всё равно проходит проверку
corp-токена, санитайзер, DLP-гейт и аудит, а отказ здесь ничего не разрешает.

### Следствия, которые надо знать

- **Предварительного подсчёта токенов больше нет.** Оба маршрута подсчёта
  токенов и `POST /utils/token_counter` (безусловно — гейт читает
  `(method, path)`, но никогда не строку запроса) отклоняются.
  `usage.input_tokens` в каждом реальном ходе — точный счёт после санитизации;
  компромисс и пункт бэклога записаны в §11 (i).
- **`POST /api/event_logging/batch` отвечает 403.** Это пакет телеметрии Claude
  Code: хука нет, и в нём то, что клиент решил туда положить. Поэтому
  клиентская телеметрия отбрасывается на шлюзе — это принято, потому что
  альтернатива — неклассифицированное тело, уходящее за периметр.
- **Админский UI и админский API litellm не отдаются.** `ast` не видит внутрь
  смонтированного ASGI-приложения, поэтому `/ui`, `/swagger`, `/docs`,
  `/openapi.json` и другие mount-ы не получают записи в таблице и отклоняются
  как отсутствующие в ней. Админский JSON API (`/key/*`, `/team/*`, …)
  закреплён как REFUSE маршрут за маршрутом — см. «Управляющая поверхность
  запрещена» выше.
- **`HEAD` на маршрут litellm отвечает 405, а не отказом.** Правило гейта:
  HEAD наследует вердикт GET для своего пути, поэтому он допускается. Но
  `APIRoute` из FastAPI, в отличие от обычного `Route` из Starlette, не добавляет
  HEAD к GET-маршруту, поэтому litellm отвечает 405. Собственные
  `HEAD /healthz/*` шлюза отвечают 200.
- **Недоступное хранилище конфигурации команд останавливает каждый
  переписываемый запрос.** Guardrail читает конфигурацию команды на каждом
  запросе, даже для команды без профилей, и хранилище, не ответившее в свою
  границу (5 с), даёт 503 `E_PROFILE_UNAVAILABLE` с
  `gateway_failure{component="team_config"}` — fail-closed, никогда не пропуск
  без профиля (`docs/ops/runbook.md`).
- **Фоновые ответы не поддерживаются, но и не блокируются.** `POST /v1/responses`
  с `background: true` допускается, и тело в апстрим санитизируется, но затем
  клиент опрашивает `GET /v1/responses/{id}`, который выполняется под другим
  request id. Cache B привязан к разговору, а `conversation_id == request_id`,
  поэтому де-санитизация опрошенного результата не гарантируется. Ни создание,
  ни опрос не возвращают оригинал. Через compose-фронт опрос туда даже не
  доходит: nginx отвечает на `GET /v1/responses/{id}` 404.

### Расширение

Выключателя нет. `CORP_LLM_ROUTE_GATE_EXTRA_PASSTHROUGH` принимает элементы
`"METHOD /path"`, через запятую или перевод строки, и может добавлять только
записи **PASSTHROUGH**: он никогда не допустит маршрут как переписываемый,
никогда не перекроет REFUSE и никогда не выключит гейт. Оба правила
проверяются дважды. При загрузке элемент, который некорректен или называет
отклонённый маршрут — включая `HEAD` на путь, чей `GET` отклонён, — это ошибка
конфигурации: `config check` сообщает о ней, а точка входа завершается с кодом
78. Сообщение об ошибке называет номер элемента и, если элемент разбирается,
только `METHOD path` — само значение переменной окружения в stdout не попадает.
В рантайме таблицы отвечают раньше любого extra, в том числе для `HEAD`, так что
extra доходит только до пары, которой нет ни в одной таблице. Используйте его для
операторского маршрута, который доказуемо никуда не отправляет пользовательский
текст.

Каждый элемент — это **ровно одна пара `(method, path)`**: префиксной формы нет,
поэтому расширение не может случайно открыть целое дерево. По той же причине им
нельзя снова открыть и админский UI: смонтированное под-приложение отдаёт много
путей под своим префиксом, и перечислять их по одному — не то расширение,
которое кто-то должен писать. `gateway-admin config check --routes` печатает
действующую таблицу и все extra.

Входная дверь nginx (`compose/nginx/`; справочник для оператора —
`compose/README.ru.md`, «HTTPS-фронт (nginx)») запрещает те же маршруты на
периметре ответом 404 и не пропускает ничего, что отклоняет гейт
(`tests/compose/test_nginx_allowlist_routes.py`). Это эшелонированная защита, а не
замена: гейт работает внутри образа, поэтому он действует и на пути через
SSH-туннель, и на compose-стеке без профиля, где nginx нет.

## 15. Интеграция с guardrail-механизмом litellm

Шлюз подключён к litellm (закреплённая версия 1.101.0) как **один обычный
callback `CustomLogger`**: `CorpLlmGuardrail` (`litellm_hook.py`), регистрация
через `litellm_settings.callbacks: ["corp_llm_gateway.bootstrap.guardrail"]`.
Рядом с этим швом litellm поставляет целый guardrail-фреймворк: базовый класс
`CustomGuardrail` с единым `apply_guardrail`, обработчики трансляции по
эндпоинтам, реестр guardrail-ов, политики и pipeline-ы, балансировку guardrail-ов

### Почему базовый класс остаётся обычным `CustomLogger`

Цикл pre-call litellm запускает обычный `CustomLogger` на каждом запросе: для него
нет ни пропуска по pipeline, ни подмены по имени. И то и другое есть только у
`CustomGuardrail` (hazards 14 и 15b); любой зарегистрированный `CustomGuardrail`
ещё и включает per-chunk хуки для всех callback-ов (hazard 12). Всё, что дал бы
базовый класс, доступно и без него. Переход ничего не даёт и создаёт три обхода.
Закреплено тестом
`tests/litellm_hook/test_acceptance_matrix.py::test_the_guardrail_stays_a_plain_custom_logger`.

**Если переход всё же выберут, sentinel-а мало.** Второй обычный callback после
нашего, который отказывает запросу без отметки нашего pre-call, ловит все обходы,
где наш pre-call не запускался (каждый путь pipeline из hazard 14 и 15b), но **не** ловит `scan_raw_request`
(hazard 11): litellm запускает наш pre-call на снимке с тем же call id, отметка
ставится, а переписанный запрос отбрасывается
(`test_fail_open_probes.py::test_sentinel_does_not_catch_scan_raw_request`).
Отметка доказывает «наш pre-call запускался», а не «живой запрос переписан».

### Граница ответа

`DesanitizeMiddleware` (`route_gate/desanitize_middleware.py`) стоит внутри
лимитера, перед приложением litellm, оборачивает только `send` и является
единственной обратной подстановкой шлюза.

- **Корреляция** — по `RequestTicket` шлюза (`inflight.current_ticket()`), не по
  `x-litellm-call-id`.
- **Состояние** — маппинг лежит в собственном хранилище middleware
  (`ResponseMappings`), не в метаданных litellm и не в аудите, и не зависит от TTL
  Cache B. Освобождается на финальном теле в любом режиме, при раскрутке запроса
  и при закрытии тикета.
- **Граница исключений** — до `http.response.start` клиент получает 500
  `E_INTERNAL` без содержимого; после — уже восстановленные события уходят, а
  поток закрывается пустым финальным телом. Строка
  `gateway_desanitize_failed request_id=… phase=… error=<тип>` и
  `gateway_failure{component="desanitize"}`.
- **Форматы** — unary JSON (с пересчётом `Content-Length`), SSE chat / Anthropic
  через `SseStreamDesanitizer`, события Responses через
  `ResponsesStreamDesanitizer`. Ответ с `Content-Encoding` проходит без
  восстановления; компрессор в приложении litellm — exit 70.
- **Счётчики токенов** читаются из ответа; chat-поток всегда запрашивает usage-чанк
  и отбрасывает его, если клиент его не просил.

Известные ограничения: чередующиеся фрагменты двух вызовов инструментов в
chat-потоке приходят клиенту плейсхолдерами, никогда не оригиналами;
`sequence_number` в восстановленном потоке Responses перенумеровывается подряд и
может отличаться от номеров провайдера; поля из открытых строк «Не санитизируется /
отложено» (§2) не восстанавливаются.

### Итоговая аудит-запись

У запроса, прошедшего pre-call, ровно одна аудит-запись, и её пишет не callback
litellm, а `route_gate/terminal_audit.py` — из фактов без контента, которые
pre-call кладёт на тикет. Порядок решения: `failed` + `E_INTERNAL` за сбой
восстановления стоит всегда; исход, опубликованный на пути ответа (`ok` или
`failed`), стоит против более поздней отмены, кроме опубликованного после ухода
клиента — это `cancelled` + `E_CLIENT_DISCONNECTED`; иначе решает закрытие тикета —
`cancelled` + `E_CLIENT_DISCONNECTED` или `E_SERVER_SHUTDOWN`, либо `failed` +
`E_INTERNAL`. Неудачная запись пути ответа повторяется один раз — закрытием; у
записи, исход которой решает закрытие (ничего не опубликовано), повтора нет;
потерянная считается в
`gateway_failure{component="desanitize"}`. Поля — [`audit-schema.ru.md`](audit-schema.ru.md).

### Отказы при взведении (exit 70)

`guardrail_absent`, `apply_guardrail`, `scan_raw_request`, `run_in_parallel`,
`litellm_debug_logging`, `litellm_set_verbose`, `response_compressor` — по строке
`arm refused (<problem>)` на каждую проблему (`route_gate/arm_checks.py`).
`CORP_LLM_ALLOW_LITELLM_DEBUG=1` пропускает две DEBUG-проблемы вне prod, только
для тестов; в prod это exit 78.

### Что litellm логирует о запросе (hazards 17-19)

Каждый callback в `litellm.callbacks` получает то, что litellm строит из своего
снимка запроса: kwargs логирования, `StandardLoggingPayload`, строку spend-log.
Pre-call подменяет в снимке контент на переписанный (17), переписывает
content-ключи снимка тела до Stage 5 (17b) и срезает `X-Corp-Auth` из каждой
копии заголовков (18). Две DEBUG-строки litellm до нашего хука («Request Headers»
и «[PROXY] returned data from litellm_pre_call_utils») печатают сырой корп-токен, а
вторая — ещё и BYOK `Authorization`; их закрывает только отказ DEBUG при
взведении. Bearer разработчика litellm хэширует (19); ключ провайдера в kwargs
логирования остаётся сырым (19b, §11 (j)).

### БД litellm

Поставляемые конфиги закрепляют `general_settings.supported_db_objects: ["models"]`
(14a). Таблица `LiteLLM_Config` (14c, открыто) доступна только в compose
(`DATABASE_URL` + `STORE_MODEL_IN_DB=True`; в Helm у litellm нет БД): строка
`litellm_settings` может добавить callback-и логирования, строка
`general_settings` — включить промпты в spend-log и другие настройки. Такой
callback видит только плейсхолдеры. Подробности и варианты для DRI — EN §15.
