# Режимы развёртывания

Какой стек поднимать, как аутентифицируются разработчики и как включать/выключать
две опциональные сетевые зависимости (корп-LLM-оракул и сервис корп-NER).
Английский оригинал: `deployment-modes.md`.

Режима аутентификации два, и они **взаимоисключающие**. Выбирайте до того, как
писать `.env`.

| | Режим A — API-ключи | Режим B — подписка (OAuth) |
|---|---|---|
| Стек | `compose/` (production) | `docker-compose.demo.yml` + `docker-compose.anthropic-oauth.yml` |
| Credential наверх | собственные `ANTHROPIC_API_KEY` / `OPENAI_API_KEY` шлюза | OAuth-токен самого разработчика, пробрасывается |
| Разработчик шлёт | `Authorization: Bearer <виртуальный ключ litellm>` | `Authorization: Bearer <OAuth-токен>` |
| `LITELLM_MASTER_KEY` | **обязателен** | **должен отсутствовать** |
| Отзыв ключа / учёт расходов по разработчику | да, через LiteLLM Admin UI | нет |

---

## Режим A — API-ключи (production-стек compose)

Стек в `compose/`. Разработчики аутентифицируются **виртуальным ключом LiteLLM**;
провайдерские credential'ы держит шлюз.

```
cd compose
cp .env.example .env
chmod 0600 .env
# заполнить обязательные секреты, затем:
docker compose up -d
```

Обязательны в `.env` (без них compose не стартует):
`POSTGRES_PASSWORD`, `LITELLM_MASTER_KEY`, `UI_USERNAME`, `UI_PASSWORD`,
`CORP_LANGFUSE_PUBLIC_KEY`, `CORP_LANGFUSE_SECRET_KEY` и секреты `LANGFUSE_*`.
См. `compose/README.md`.

**Ключи провайдеров — опциональны.** В `docker-compose.yml` они объявлены как
`${ANTHROPIC_API_KEY:-}` / `${OPENAI_API_KEY:-}`, то есть пустое значение
допустимо. Задавайте только то, куда реально ходите:

- `ANTHROPIC_API_KEY` — нужен для маршрута `claude-*`;
- `OPENAI_API_KEY` — нужен для маршрута `gpt-*`;
- ни одного — нормально, если используете только маршрут `corp-*` на корп-vLLM.

**BYOK в этом режиме недоступен ни на одном маршруте.** Нативные провайдеры
`anthropic/` и `openai/` строят upstream-credential из настроенного `api_key` и
инбаундный заголовок `Authorization` не читают вообще; маршрут `corp-*` /
`hosted_vllm/` ведёт себя так же. Собственный ключ разработчика сюда не доедет —
для этого существует режим B.

## Режим B — подписка (проброс OAuth)

Токен подписки Anthropic разработчика пробрасывается на `api.anthropic.com` без
изменений. **Никакого `ANTHROPIC_API_KEY` в этом режиме нет вообще.**

```
docker compose -f docker-compose.demo.yml -f docker-compose.anthropic-oauth.yml up -d --build
```

Оверлей накладывается именно на **demo**-стек, и это намеренно: в том стеке не
задан `LITELLM_MASTER_KEY`. Мост включается переменной
`CORP_LLM_FORWARD_ANTHROPIC_AUTH=1` (оверлей выставляет её сам).

**Мастер-ключ и мост несовместимы.** При заданном мастер-ключе litellm трактует
входящий `Authorization` как один из своих виртуальных ключей и отвечает 401
*до* того, как отработает `pre_call`, — OAuth-токен до моста не дойдёт никогда.
Поэтому `build_guardrail()` отказывается стартовать и называет причину
(`settings.MASTER_KEY_VS_FORWARD_AUTH_MESSAGE`), вместо того чтобы молча отдавать
401.

> **Ловушка:** пустая строка `LITELLM_MASTER_KEY=` **считается заданной** —
> litellm сохраняет пустое значение и включает proxy-auth для всего, что не
> `None`. Удаляйте строку целиком. Обычный источник проблемы — забытый ключ в
> git-ignored `.env.demo`, который подтягивается через `env_file:`.

Что учесть при планировании: в режиме B **нет виртуальных ключей на
разработчика**, а значит нет ни отзыва, ни учёта расходов по конкретному
человеку через UI. Санитизация, аудит и командная идентичность `X-Corp-Auth`
работают одинаково в обоих режимах.

## Переключатель: корп-LLM-оракул

Оракул — это **условный fallback** в конце локального каскада (ADR-003). Он
вызывается только при детерминированном попадании в газеттир, а не на каждый
запрос.

**Выключен (по умолчанию).** В `compose/.env.example` стоит
`CORP_LLM_ORACLE_ENABLED=0`. В этом состоянии вызов оракула не делается никогда,
и `CORP_LLM_ENDPOINT` для детекции не нужен.

**Включение.**

```
CORP_LLM_ORACLE_ENABLED=1
CORP_LLM_ENDPOINT=https://<хост-корп-vllm>/v1   # обязателен, когда оракул включён
```

Три вещи, на которых спотыкаются:

- **Включение без доступного endpoint'а роняет запросы fail-closed на *всех*
  маршрутах**, а не только на `corp-*`: попадание в газеттир уходит на
  немаршрутизируемый placeholder-хост. Сначала направьте `CORP_LLM_ENDPOINT` на
  живой vLLM.
- **Маршруту `corp-*` `CORP_LLM_ENDPOINT` нужен независимо от этого флага.** Без
  него запросы `corp-*` падают по одному, а не на загрузке конфига.
- **Нельзя выключить одновременно оракул и локальный каскад.**
  `build_guardrail()` на старте бросит `ConfigError(NO_OP_SANITIZER_MESSAGE)`,
  если `CORP_LLM_ORACLE_ENABLED=0` **и** `CORP_LLM_LOCAL_FIRST=0`, — шлюз
  отказывается работать как no-op-санитайзер. На этом стеке
  `CORP_LLM_LOCAL_FIRST` не задан и берёт значение по умолчанию `1`, так что
  штатная поза безопасна; просто не ставьте `0`, не включив оракул.

**Когда именно он срабатывает** — задаёт `CORP_LLM_ORACLE_TRIGGER`:
`gazetteer_hit` (по умолчанию) | `any_local_finding` | `always` |
`sampled:<pct>`. Профиль команды может расширить это через `oracle_mode`;
эффективное значение — **более широкое** из двух, сузить ни одно из них не может.

## Переключатель: сервис корп-NER

Удалённый NER-детектор, добавляемый в локальный каскад. Ходит **по сети**,
поэтому исключён из сегментов `CODE` (иначе исходники ушли бы во внешний
сервис); все локальные детекторы `CODE` продолжают сканировать.

**Выключен (по умолчанию).** `CORP_NER_ENABLED=0`. Стек ведёт себя ровно так,
как будто фичи не существует: ни детектора, ни readiness-пробы.

**Включение.** Обе переменные нужны вместе:

```
CORP_NER_ENABLED=1
CORP_NER_ENDPOINT=http://<хост-ner>:<порт>      # БАЗОВЫЙ url; клиент сам добавит /v1/analyze
```

- **Включено без endpoint'а — это отказ на старте**, а не тихий пропуск:
  `build_corp_ner()` бросает `ConfigError`, и `gateway-admin config check`
  сообщает о той же проблеме.
- **Нужна сборка из исходников.** Опубликованный `GATEWAY_IMAGE_TAG`
  (`1.0.0-rc.6`, коммит `1f170ea`) — *предок* ветки, добавившей корп-NER, поэтому
  на том образе эти переменные не делают ничего. Используйте
  `docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build`.
- Опциональный тюнинг передаётся **по «голому» имени** (оставляйте строки
  закомментированными, а не пустыми — пустая переменная окружения побеждает
  конфиг-файл): `CORP_NER_TIMEOUT_S` (30), `CORP_NER_MAX_TEXTS` (256),
  `CORP_NER_MAX_INPUT_CHARS` (200000), `CORP_NER_CA_BUNDLE` (не задан).
- Вызов NER несёт **сырой пользовательский контент**, поэтому проверка TLS для
  него не отключается никогда. Для внутреннего CA укажите цепочку в
  `CORP_NER_CA_BUNDLE`.

**Переключение любого из флагов безопасно для Cache A.** В ключ кэша входит
отпечаток эффективной политики детекторов, поэтому pod'ы с разными значениями
`CORP_NER_ENABLED` получают непересекающиеся ключи и не могут отдать друг другу
чужие записи. Чистить кэш не нужно — см. `upgrade.md`.

Не путайте `CORP_NER_ENABLED` (этот удалённый сервис) с `CORP_LLM_REQUIRE_NER`
(**внутрипроцессные** RU/EN-движки), который в production остаётся `1` в любом
случае.
