# corp-llm-gateway — инструкция по развёртыванию

Передаточный документ для девопса. Сжатая последовательность действий; полная
матрица режимов и все режимы отказа — в `deployment-modes.ru.md`, справочник по
переменным — в `configuration.md`, дежурные процедуры — в `runbook.ru.md`.
Английская версия: `deploy-handoff.md`.

## Что разворачиваем

Шлюз между Claude Code разработчиков и внешними LLM (Anthropic / OpenAI). Он
вычищает персональные данные и корпоративные секреты из запроса **до** того, как
тот покинет периметр, и восстанавливает их в ответе. Всё, что уходит наверх,
пишется в аудит.

Стек (docker compose, один хост): `litellm` (шлюз), `postgres` (токены команд +
конфиг команд + БД виртуальных ключей litellm), `redis` (маппинги для обратной
подстановки), `langfuse` + `clickhouse` + `minio` (трейсы и аудит), `vector`
(доставка аудита).

---

## Шаг 0. Требования к хосту

- Debian/Ubuntu или RHEL-семейство. Другие дистрибутивы скрипт подготовки
  отказывается обслуживать, а не угадывает.
- Docker Engine + плагин compose v2. Скрипт установит их сам с официального
  репозитория Docker, если нет.
- **CPU-only.** GPU не нужен и не поддерживается.
- Диск: с запасом под логи docker'а и буфер Vector — по умолчанию ~1 ГиБ на
  ротацию логов litellm плюс 1 ГиБ дискового буфера Vector.
- Исходящий доступ: `api.anthropic.com` и/или `api.openai.com`; плюс корп-vLLM и
  сервис корп-NER, если они включаются.

## Шаг 1. Подготовка сервера (день 0, один раз, на самом сервере)

```
sudo scripts/deploy/bootstrap-server.sh
```

Что делает: проверяет/ставит Docker, создаёт `/opt/corp-llm-gateway`, кладёт туда
`.env` из шаблона с правами `0600` — **и выходит с кодом 1**, чтобы вы сначала
заполнили `.env`. Это ожидаемое поведение, а не ошибка.

**`--systemd` на этом запуске передавать рано:** юнит автозапуска ставится только
когда в каталоге уже лежат compose-файлы, иначе он падал бы при каждой загрузке.
Вернитесь к нему после шага 5:

```
sudo scripts/deploy/bootstrap-server.sh --systemd
```

Скрипт идемпотентный: существующие `.env`, каталог, репозиторий пакетов и
systemd-юнит не перезаписываются.

## Шаг 2. Заполнить `.env`

Файл `/opt/corp-llm-gateway/.env`, права `0600`. Он существует **только на
сервере** — скрипт развёртывания его никогда не загружает, не читает и не
печатает.

Без этих ключей `docker compose` откажется стартовать с явным сообщением
«set X in .env»:

| Ключ | Как получить |
|---|---|
| `POSTGRES_PASSWORD` | `openssl rand -hex 32` |
| `GATEWAY_IMAGE_TAG` | уже заполнен (`1.0.0-rc.6`), см. шаг 3 |
| `LANGFUSE_POSTGRES_PASSWORD` | `openssl rand -hex 32` |
| `LANGFUSE_CLICKHOUSE_PASSWORD` | `openssl rand -hex 32` |
| `MINIO_ROOT_PASSWORD` | `openssl rand -hex 32` |
| `LANGFUSE_NEXTAUTH_SECRET` | `openssl rand -base64 32` |
| `LANGFUSE_SALT` | `openssl rand -base64 32` |
| `LANGFUSE_ENCRYPTION_KEY` | `openssl rand -hex 32` — **ровно 64 hex-символа**; смена ключа позже делает уже зашифрованные строки нечитаемыми |
| `CORP_LANGFUSE_PUBLIC_KEY` | ключ проекта Langfuse `pk-lf-…`, см. ниже |
| `CORP_LANGFUSE_SECRET_KEY` | ключ проекта Langfuse `sk-lf-…`, см. ниже |

Дальше — в зависимости от режима, см. шаг 4.

### Про пару ключей Langfuse — прочитать до первого старта

`CORP_LANGFUSE_PUBLIC_KEY` / `CORP_LANGFUSE_SECRET_KEY` — это **ключи проекта
Langfuse**, а не инфраструктурные секреты `LANGFUSE_*` из таблицы выше. Ими
аутентифицируется Vector, доставляющий аудит.

Пустые значения безопасны: `docker compose config` упадёт, Vector не стартует,
ничего не теряется — при первом запуске он читает лог с самого начала.
**Неправильные значения — не безопасны:** Vector стартует, Langfuse отвечает 401,
а его HTTP-sink не повторяет попытку при ошибке аутентификации (только на
408/429/5xx) — эти записи аудита будут **потеряны**.

Проще всего избежать проблемы через headless-инициализацию: раскомментируйте
блок `LANGFUSE_INIT_*` в `.env` и задайте `LANGFUSE_INIT_PROJECT_PUBLIC_KEY` /
`_SECRET_KEY` теми же значениями, что и `CORP_LANGFUSE_*`. Тогда проект, первый
пользователь и ключи создаются на первом же старте.

Если заводите проект через UI — держите Vector вне стека, пока не впишете
реальные ключи: `docker compose up -d --scale vector=0`.

## Шаг 3. Выбрать образ

`GATEWAY_IMAGE_TAG=1.0.0-rc.6` — опубликованный образ. Он **старше** ветки,
добавившей интеграцию с корп-NER, правило Luhn для банковских карт и исправления
границы Cache A.

- Корп-NER **не нужен** → оставляйте тег как есть, образ тянется готовым.
- Корп-NER **нужен** → собирайте из исходников:

```
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

Оверлей сборки намеренно ставит NER-профиль `ru-en`: в профиле по умолчанию
(`base`) нет английской модели, а стек идёт с `CORP_LLM_REQUIRE_NER=1`, и такой
образ отвечал бы 503 на каждый запрос.

## Шаг 4. Выбрать режим аутентификации

Режима два, они **взаимоисключающие**, и оба — production. Решение принимается
до заполнения `.env`.

### Режим A — корпоративные API-ключи

Ключи провайдеров держит шлюз. Разработчики ходят с **виртуальным ключом
LiteLLM**, который выдаётся в админ-UI; по нему есть отзыв и учёт расходов
на конкретного человека.

Дополнительно в `.env`:

| Ключ | Значение |
|---|---|
| `LITELLM_MASTER_KEY` | `sk-` + `openssl rand -hex 32` |
| `UI_USERNAME`, `UI_PASSWORD` | учётка админ-UI |
| `ANTHROPIC_API_KEY` | нужен для маршрута `claude-*` |
| `OPENAI_API_KEY` | нужен для маршрута `gpt-*` |

Ключи провайдеров **опциональны**: задавайте только те, куда реально ходите.
Если используется только корп-vLLM (`corp-*`) — можно ни одного.

Запуск:

```
cd /opt/corp-llm-gateway
docker compose up -d
```

Если `LITELLM_MASTER_KEY`, `UI_USERNAME` или `UI_PASSWORD` не заданы, контейнер
откажется стартовать и назовёт переменную. Это защита, а не придирка: без
мастер-ключа litellm полностью пропускает свою проверку авторизации, то есть
пропажа ключа тихо убрала бы единственный per-developer credential этого режима.

### Режим B — подписка разработчика (OAuth)

Токен подписки Anthropic (Max/Pro) самого разработчика пробрасывается наверх без
изменений. **Корпоративного `ANTHROPIC_API_KEY` в этом режиме нет вообще.**

В `.env`:

- **удалить целиком три строки**: `LITELLM_MASTER_KEY`, `UI_USERNAME`,
  `UI_PASSWORD`;
- **раскомментировать** `COMPOSE_FILE=docker-compose.yml:docker-compose.oauth.yml`.

Вторая строка нужна для автозапуска: systemd-юнит выполняет голый
`docker compose up -d`, и без неё после перезагрузки хоста стек пытался бы
подняться в режиме A. Он при этом падает громко, а не работает не в том режиме,
но лежать будет, пока его не поднимут руками.

> **Не оставлять пустыми.** Пустая строка `LITELLM_MASTER_KEY=` считается
> заданной: litellm сохраняет пустое значение и включает proxy-auth для всего,
> что не `None`. Шлюз в этом случае откажется стартовать с явной причиной —
> лучше, чем молча отдавать 401 на каждый запрос. Удаляйте строку, а не
> значение.

Запуск:

```
cd /opt/corp-llm-gateway
docker compose -f docker-compose.yml -f docker-compose.oauth.yml up -d
```

Что меняет оверлей: включает мост `CORP_LLM_FORWARD_ANTHROPIC_AUTH=1` и
подменяет конфиг litellm на Anthropic-only. Postgres, Redis, Langfuse и Vector —
без изменений, аудит работает так же, как в режиме A.

**В этом режиме обслуживается только маршрут `claude-*`.** Это несущий контроль
безопасности, а не упрощение: hook разрешает подстановку OAuth-токена по видимому
клиенту алиасу модели, но litellm выбирает фактический upstream уже **после**
хука, поэтому единственная гарантия, что токен подписки не уйдёт другому
провайдеру, — отсутствие в таблице маршрутов чего-либо, кроме `anthropic/`.
Второй маршрут туда не добавлять.

Оракул на корп-vLLM при этом продолжает работать: до него шлюз ходит собственным
HTTP-клиентом, а не через маршрут litellm.

## Шаг 5. Развёртывание с ноутбука оператора (день N)

Вместо ручного `docker compose` на сервере удобнее гонять скрипт — он сам
подкладывает SQL-схему хранилища токенов, синхронизирует `compose/`, дёргает
`pull` + `up -d` и дожидается healthcheck'ов.

```
# режим A
scripts/deploy/deploy.sh --host user@server up

# режим B
scripts/deploy/deploy.sh --host user@server --mode oauth up
```

**Тот же `--mode` нужно передавать во все последующие запуски по этому хосту** —
`logs`, `status`, `down`, `restart` резолвят стек через этот список файлов.
Запуск без `--mode oauth` покажет (или пересоздаст) другой стек.

Остальные подкоманды: `down` (тома сохраняются, спрашивает подтверждение),
`restart`, `logs`, `status`. Полезные флаги: `--dry-run`, `--yes`,
`--dir PATH`, `--force-unlock`.

Локальный `.env` наверх не уезжает никогда; серверный `.env` не трогается.
Ключи и сертификаты из синхронизации исключены.

> Если разворачиваете руками, без скрипта, — перед первым стартом положите схему:
> `cp src/corp_llm_gateway/tokens/schema.sql compose/postgres/initdb/01-schema.sql`.
> Init-скрипты Postgres отрабатывают только на пустом томе, при первом запуске.

## Шаг 6. Переключатель — оракул на корп-vLLM

Оракул — это **условный fallback** в конце локального каскада детекции. Он
вызывается только при детерминированном попадании в газеттир, а не на каждый
запрос.

**Выключен по умолчанию** (`CORP_LLM_ORACLE_ENABLED=0`). В этом состоянии вызов
не делается никогда и `CORP_LLM_ENDPOINT` для детекции не нужен.

Включение:

```
CORP_LLM_ORACLE_ENABLED=1
CORP_LLM_ENDPOINT=https://<хост-корп-vllm>/v1    # обязателен, когда оракул включён
```

Три вещи, на которых спотыкаются:

- **Включить без доступного endpoint'а — уронить запросы на всех маршрутах**, а
  не только на `corp-*`: попадание в газеттир уйдёт на немаршрутизируемый
  placeholder-хост и запрос упадёт fail-closed. Сначала проверьте, что vLLM
  доступен.
- Маршруту `corp-*` `CORP_LLM_ENDPOINT` нужен **независимо** от этого флага.
- **Нельзя выключить одновременно оракул и локальный каскад.** При
  `CORP_LLM_ORACLE_ENABLED=0` и `CORP_LLM_LOCAL_FIRST=0` шлюз откажется
  стартовать — он не работает как no-op-санитайзер. `CORP_LLM_LOCAL_FIRST` на
  этом стеке не задан и по умолчанию равен `1`; просто не ставьте `0`.

Если корп-vLLM за внутренним CA — положите цепочку в
`compose/certs/corp-ca-bundle.pem` и раскомментируйте `CORP_LLM_CA_BUNDLE`.

## Шаг 7. Переключатель — сервис корп-NER

Удалённый NER-детектор, добавляемый в локальный каскад. Ходит **по сети**,
поэтому исключён из сегментов с кодом (иначе исходники ушли бы во внешний
сервис); локальные детекторы код сканировать продолжают.

**Выключен по умолчанию** (`CORP_NER_ENABLED=0`) — ни детектора, ни пробы
готовности, стек ведёт себя так, будто фичи не существует.

Включение — обе переменные вместе:

```
CORP_NER_ENABLED=1
CORP_NER_ENDPOINT=http://<хост-ner>:<порт>     # БАЗОВЫЙ url, клиент сам добавит /v1/analyze
```

- **Включено без endpoint'а — отказ на старте**, а не тихий пропуск.
- **Нужна сборка из исходников** (шаг 3): на опубликованном `1.0.0-rc.6` эти
  переменные не делают ничего.
- Тюнинг (`CORP_NER_TIMEOUT_S`, `CORP_NER_MAX_TEXTS`, `CORP_NER_MAX_INPUT_CHARS`,
  `CORP_NER_CA_BUNDLE`) — оставляйте строки **закомментированными**, а не
  пустыми: пустая переменная окружения побеждает конфиг-файл. Значения по
  умолчанию: 30 с, 256 текстов, 200000 символов, без CA.
- Вызов NER несёт **сырой пользовательский контент**, поэтому проверка TLS для
  него не отключается никогда. Внутренний CA — через `CORP_NER_CA_BUNDLE`.

Переключение любого из флагов (оракул, NER) **безопасно для кэша**: в ключ
входит отпечаток эффективной политики детекторов, поэтому записи с разными
настройками не пересекаются. Чистить кэш не нужно.

Не путайте `CORP_NER_ENABLED` (этот удалённый сервис) с `CORP_LLM_REQUIRE_NER`
(внутрипроцессные RU/EN-движки) — второй в production остаётся `1` в любом
случае.

## Шаг 8. Проверка после старта

```
docker compose ps                                   # все сервисы healthy
curl -fsS http://127.0.0.1:4000/health/liveliness    # шлюз отвечает
docker compose logs --tail=100 litellm
docker compose logs --tail=50 vector                 # аудит доставляется
```

Порт `4000` публикуется **только на loopback** (`127.0.0.1:4000`). Langfuse не
публикует хостовый порт вообще — до UI добираются SSH-туннелем (проброс
локального `3000`).

> `/health/liveliness` — это собственная проба litellm. Эндпоинты `/healthz/*`
> (`ready`, `sanitization`) на этом стеке **не смонтированы**; они относятся к
> k8s-варианту. Не закладывайте их в мониторинг compose-развёртывания.

## Шаг 9. Выдача командных токенов (`X-Corp-Auth`)

Идентичность команды — заголовок `X-Corp-Auth`. Он определяет, какие правила,
профиль и аудит применяются, и нужен **в обоих режимах**. Запрос без валидного
токена отклоняется.

```
gateway-admin team create --team-id team-x --name "Team X"
gateway-admin token issue --user alice --team team-x --ttl-days 30
gateway-admin token revoke --user alice
```

⚠️ Мутации под RBAC требуют либо `CORP_GATEWAY_ADMIN_TOKEN` (операторский JWT),
либо `CORP_GATEWAY_RBAC=0` (обход для отладки), и **ни то, ни другое не задано в
окружении контейнера**. Выставляйте на той машине, откуда запускаете CLI.
Подробности — `docs/ops/admin-cli.md`.

## Шаг 10. Подключение разработчика

**Режим A:** два заголовка на каждый запрос —
`Authorization: Bearer <виртуальный ключ litellm>` (кто вообще может обращаться к
прокси) и `X-Corp-Auth: <токен команды>` (чьи правила и аудит применяются).
Базовый URL — адрес шлюза.

**Режим B:**

```
export ANTHROPIC_AUTH_TOKEN='sk-ant-oat...'    # токен подписки разработчика
export ANTHROPIC_BASE_URL='http://<шлюз>:4000'
export ANTHROPIC_CUSTOM_HEADERS='X-Corp-Auth: <токен команды>'
unset ANTHROPIC_API_KEY                        # иначе он перекроет подписку
claude
```

Принимаются только токены вида `sk-ant-oat…`; всё остальное — `401
E_PROVIDER_AUTH`.

## Что важно знать перед вводом в эксплуатацию

- **TLS перед шлюзом ещё не сделан.** Порт слушает `127.0.0.1` без TLS; фронт на
  nginx — отдельная невыполненная задача. До неё разработчики ходят через
  SSH-туннель, а не по сети.
- **В режиме B management-эндпоинты litellm без аутентификации.** Без
  мастер-ключа его proxy-auth пропускается целиком. Это касается `/key/*`,
  `/model/*`, `/user/*` и UI — **не** LLM-маршрутов, их по-прежнему закрывает
  проверка `X-Corp-Auth`. Сейчас поверхность доступна только с самого хоста
  (loopback), но доступна любому, у кого там есть shell. Когда появится nginx,
  этот контур обязан быть закрыт там **до** вывода порта за loopback. В режиме A
  разрыва нет — эти эндпоинты закрывает мастер-ключ.
- **Никакого недоверенного `docker run` на этом хосте.** Метка контейнера, по
  которой Vector отбирает записи аудита, публична: любой, кто может запускать
  контейнеры на этом хосте, может подделать записи. Это жёсткое требование
  модели развёртывания, а не рекомендация.
- **Аудит буферизуется, но не fail-closed.** Дисковый буфер Vector (по умолчанию
  1 ГиБ) переживает недоступность Langfuse; после его заполнения записи ждут в
  лог-файлах docker'а, то есть реальная граница долговечности — ротация логов
  (по умолчанию 100 МБ × 10). Если Langfuse может лежать дольше — поднимайте оба
  значения вместе.
- **Не выполнять `FLUSHDB` на redis шлюза.** Там лежат маппинги, без которых
  ответ не восстановится в исходный вид.
- **Отзыв виртуального ключа существует только в режиме A.** В режиме B нет ни
  per-developer отзыва, ни учёта расходов на человека.
