# corp-llm-gateway — инструкция по развёртыванию

Передаточный документ для девопса. Сжатая последовательность действий;
провайдеры и все режимы отказа — в `deployment-modes.ru.md`, справочник по
переменным — в `configuration.md`, дежурные процедуры — в `runbook.ru.md`.
Английская версия: `deploy-handoff.md`.

## Что разворачиваем

Шлюз между Claude Code / Codex разработчиков и LLM (Anthropic, ChatGPT Codex,
корп-vLLM). Он
вычищает персональные данные и корпоративные секреты из запроса **до** того, как
тот покинет периметр, и восстанавливает их в ответе. Всё, что уходит наверх,
пишется в аудит.

Стек (docker compose, один хост): по шлюзу на провайдера — `gateway-anthropic`,
`gateway-codex`, `gateway-corp`, каждый включается своим профилем compose — плюс
`profile-guard` (отказывает стеку без провайдера), `postgres` (токены команд +
конфиг команд, общие для всех шлюзов), `redis` (маппинги для обратной
подстановки), `langfuse` + `clickhouse` + `minio` (трейсы и аудит), `vector`
(доставка аудита). Обновление хоста 1.0: `upgrade.md`, «1.0 → 1.1.0».

---

## Шаг 0. Требования к хосту

- Debian/Ubuntu или RHEL-семейство. Другие дистрибутивы скрипт подготовки
  отказывается обслуживать, а не угадывает.
- Docker Engine + плагин compose v2. Скрипт установит их сам с официального
  репозитория Docker, если нет.
- **CPU-only.** GPU не нужен и не поддерживается.
- Диск: с запасом под логи docker'а и буфер Vector — по умолчанию ~1 ГиБ
  ротации логов на каждый шлюз плюс 1 ГиБ дискового буфера Vector.
- Исходящий доступ, по провайдерам: `api.anthropic.com` (`anthropic`),
  `chatgpt.com` (`codex`), корп-vLLM (`corp`, и оракул, если включён); плюс
  сервис корп-NER, если он включается.

## Шаг 1. Подготовка сервера (день 0, один раз, на самом сервере)

```
sudo scripts/deploy/bootstrap-server.sh
```

Что делает: проверяет/ставит Docker, создаёт `/opt/corp-llm-gateway`, кладёт туда
`.env` из шаблона с правами `0600` — **и выходит с кодом 1**, чтобы вы сначала
заполнили `.env`. Это ожидаемое поведение, а не ошибка.

**`--systemd` на этом запуске передавать рано:** юнит автозапуска ставится только
когда в каталоге уже лежат compose-файлы, иначе он падал бы при каждой загрузке.
Вернитесь к нему после шага 5:

```
sudo scripts/deploy/bootstrap-server.sh --systemd
```

Скрипт идемпотентный: существующие `.env`, каталог, репозиторий пакетов и
systemd-юнит не перезаписываются.

## Шаг 2. Заполнить `.env`

Файл `/opt/corp-llm-gateway/.env`, права `0600`. Он существует **только на
сервере** — скрипт развёртывания его никогда не загружает, не читает и не
печатает.

Без этих ключей `docker compose` откажется стартовать с явным сообщением
«set X in .env»:

| Ключ | Как получить |
|---|---|
| `COMPOSE_PROFILES` | провайдеры этого хоста, см. шаг 4 (без провайдера `profile-guard` отказывает) |
| `POSTGRES_PASSWORD` | `openssl rand -hex 32` |
| `GATEWAY_IMAGE_TAG` | уже заполнен (`1.0.0-rc.6`), см. шаг 3 |
| `LANGFUSE_POSTGRES_PASSWORD` | `openssl rand -hex 32` |
| `LANGFUSE_CLICKHOUSE_PASSWORD` | `openssl rand -hex 32` |
| `MINIO_ROOT_PASSWORD` | `openssl rand -hex 32` |
| `LANGFUSE_NEXTAUTH_SECRET` | `openssl rand -base64 32` |
| `LANGFUSE_SALT` | `openssl rand -base64 32` |
| `LANGFUSE_ENCRYPTION_KEY` | `openssl rand -hex 32` — **ровно 64 hex-символа**; смена ключа позже делает уже зашифрованные строки нечитаемыми |
| `CORP_LANGFUSE_PUBLIC_KEY` | ключ проекта Langfuse `pk-lf-…`, см. ниже |
| `CORP_LANGFUSE_SECRET_KEY` | ключ проекта Langfuse `sk-lf-…`, см. ниже |

`LITELLM_MASTER_KEY`, `UI_USERNAME`, `UI_PASSWORD`, `ANTHROPIC_API_KEY` и
`OPENAI_API_KEY` ушли вместе с режимом A (1.1.0): стек не передаёт шлюзу ни один
из них, так что их не задавайте. Мастер-ключ, заданный там, откуда шлюз его
читает (его файл конфигурации, переопределение окружения), не даёт стартовать,
пустой в том числе.

### Про пару ключей Langfuse — прочитать до первого старта

`CORP_LANGFUSE_PUBLIC_KEY` / `CORP_LANGFUSE_SECRET_KEY` — это **ключи проекта
Langfuse**, а не инфраструктурные секреты `LANGFUSE_*` из таблицы выше. Ими
аутентифицируется Vector, доставляющий аудит.

Пустые значения безопасны: `docker compose config` упадёт, Vector не стартует,
ничего не теряется — при первом запуске он читает лог с самого начала.
**Неправильные значения — не безопасны:** Vector стартует, Langfuse отвечает 401,
а его HTTP-sink не повторяет попытку при ошибке аутентификации (только на
408/429/5xx) — эти записи аудита будут **потеряны**.

Проще всего избежать проблемы через headless-инициализацию: раскомментируйте
блок `LANGFUSE_INIT_*` в `.env` и задайте `LANGFUSE_INIT_PROJECT_PUBLIC_KEY` /
`_SECRET_KEY` теми же значениями, что и `CORP_LANGFUSE_*`. Тогда проект, первый
пользователь и ключи создаются на первом же старте.

Если заводите проект через UI — держите Vector вне стека, пока не впишете
реальные ключи: `docker compose up -d --scale vector=0`.

## Шаг 3. Выбрать образ

`GATEWAY_IMAGE_TAG=1.0.0-rc.6` — опубликованный образ. Он **старше** ветки,
добавившей интеграцию с корп-NER, правило Luhn для банковских карт и исправления
границы Cache A.

- Корп-NER **не нужен** → оставляйте тег как есть, образ тянется готовым.
- Корп-NER **нужен** → собирайте из исходников:

```
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --build
```

Оверлей сборки намеренно ставит NER-профиль `ru-en`: в профиле по умолчанию
(`base`) нет английской модели, а стек идёт с `CORP_LLM_REQUIRE_NER=1`, и такой
образ отвечал бы 503 на каждый запрос.

## Шаг 4. Выбрать провайдеров

Каждый провайдер — отдельный контейнер шлюза. Выберите хотя бы одного, в `.env`:

```
COMPOSE_PROFILES=anthropic            # например anthropic,codex или anthropic,codex,corp
```

| Провайдер | Что обслуживает | Credential наверх | Порт на `127.0.0.1` |
|---|---|---|---|
| `anthropic` | Claude Code на подписке Anthropic разработчика (`claude-*`) | токен `sk-ant-oat…` разработчика | 4000 (`GATEWAY_ANTHROPIC_PORT`) |
| `codex` | Codex на подписке ChatGPT разработчика | токен ChatGPT разработчика | 4001 (`GATEWAY_CODEX_PORT`) |
| `corp` | корп-vLLM (`corp-*`); задайте `CORP_LLM_ENDPOINT` | `CORP_LLM_AUTH_TOKEN` (пустой для vLLM без аутентификации) | 4002 (`GATEWAY_CORP_PORT`) |

**Корпоративного ключа API провайдера нет нигде.** Подписочные провайдеры
пробрасывают собственный токен разработчика; провайдер corp отправляет свой
настроенный.

`COMPOSE_PROFILES` — единственный переключатель. У `deploy.sh` для него нет
флага, и он его никогда не выставляет, а юнит автозапуска читает тот же `.env`,
поэтому после перезагрузки поднимаются те же провайдеры. Без провайдера
`profile-guard` завершается с кодом 64, называя ключ, и `up` падает (`postgres` его ждёт).
Считаются только точные имена (`corporate` — не `corp`), а `--profile` в
командной строке не поддерживается.

**У конфига litellm каждого провайдера один маршрут, и это несущий контроль
безопасности.** Hook подставляет подписочный токен по видимому клиенту алиасу
модели, но litellm выбирает фактический upstream уже **после** хука, поэтому
единственная гарантия, что токен не уйдёт другому провайдеру, — сама таблица
маршрутов: только `anthropic/` на `gateway-anthropic`, литеральный URL ChatGPT
Codex на `gateway-codex`. Ни в один из них маршрут не добавлять.

Оракул на корп-vLLM работает на любом провайдере: до него шлюз ходит собственным
HTTP-клиентом, а не через маршрут litellm.

## Шаг 4a. HTTPS-фронт (опционально)

Без него каждый шлюз слушает только свой порт на `127.0.0.1`, по plain HTTP, и
разработчикам нужен SSH-туннель. С ним nginx публикует один шлюз и Langfuse по
HTTPS и пропускает
только LLM-маршруты, `/v1/models`, `/healthz/live` и
`POST /internal/issue-token` — всё остальное 404. Полный справочник:
`compose/README.ru.md`, «HTTPS-фронт (nginx)».

1. **Выберите маршрутизацию.** `nginx` маршрутизирует по имени, и ему нужны две
   DNS-записи, `gateway.<домен>` и `langfuse.<домен>`, указывающие на этот хост
   (или на балансировщик перед ним). `nginx-ports` обходится без DNS: шлюз на
   `NGINX_PORT` (443), Langfuse на `NGINX_LANGFUSE_PORT` (8443).
2. **Выберите режим TLS — обязателен, умолчания нет.** Администраторы уже
   публикуют HTTPS перед этим хостом и пересылают на него HTTP внутри →
   `NGINX_TLS_MODE=behind-proxy`, плюс `NGINX_TRUSTED_PROXIES` = адрес
   балансировщика таким, каким его видит nginx. Любой другой пир не получает
   ответа вовсе, поэтому неверное значение — это недоступность: отклонённый
   адрес виден в `docker compose logs nginx` (или `nginx-ports`; статус `444`).
   Иначе → `NGINX_TLS_MODE=terminate`, и nginx нужен сертификат (пункт 4).
3. **Заполните `.env` на сервере** (закомментированный блок «nginx front door»):

   ```
   COMPOSE_PROFILES=anthropic,nginx   # провайдеры плюс nginx или nginx-ports; никогда оба
   NGINX_GATEWAY_UPSTREAM=gateway-anthropic   # по умолчанию; или gateway-codex / gateway-corp
   NGINX_TLS_MODE=terminate        # или behind-proxy
   GATEWAY_DOMAIN=corp.example     # только nginx
   NGINX_BIND_ADDR=10.1.2.3        # интерфейс, до которого доходят клиенты (или LB); по умолчанию 127.0.0.1
   NGINX_TLS_CERT=gateway.crt      # только terminate
   NGINX_TLS_KEY=gateway.key       # только terminate
   LANGFUSE_PUBLIC_URL=https://langfuse.corp.example
   ```

   `COMPOSE_PROFILES` — единственный переключатель. У `deploy.sh` для него нет
   флага, а юнит автозапуска читает тот же `.env`, поэтому после перезагрузки
   поднимается то же, что подняло развёртывание. nginx проксирует на один шлюз,
   `NGINX_GATEWAY_UPSTREAM`; его провайдер должен быть в `COMPOSE_PROFILES`,
   иначе nginx завершается с кодом 64. Остальные провайдеры остаются на своих
   loopback-портах (SSH-туннель). `NGINX_BIND_ADDR` по умолчанию —
   loopback: если его не трогать, снаружи хоста до nginx не достучаться.
   `LANGFUSE_PUBLIC_URL` должен быть публичным `https://`-origin'ом
   (`https://<адрес>:8443` при `nginx-ports`), и в `behind-proxy` тоже. Чтобы
   позже сменить или убрать профиль, запустите `deploy.sh up`: он удаляет
   контейнер фронта, который `.env` больше не выбирает. Голый
   `docker compose up -d` этого НЕ делает, и старый контейнер держит порт;
   удалите его вручную через `docker rm -f <контейнер>`.
4. **Положите сертификат на сервер** (только `terminate`): прямо в
   `/opt/corp-llm-gateway/nginx/certs/`, никогда не через синхронизацию (как
   `compose/certs/corp-ca-bundle.pem` в шаге 6, который синхронизация тоже
   исключает). Один сертификат с обоими именами в SAN (или с IP, на который
   ходят клиенты, при `nginx-ports`), полная цепочка в PEM, ключ без шифрования
   и с правами `0600`. Скрипт развёртывания туда ничего не загружает. SAN, пример
   CSR и помощник для одноразового самоподписанного сертификата —
   `compose/nginx/certs/README.md`.
5. **Ротация:** замените оба файла в том же каталоге, затем на сервере
   `docker compose restart nginx` (или `nginx-ports`). nginx читает сертификат
   только при старте и не предупреждает об истечении срока.

Неверно настроенный фронт не стартует: его entrypoint называет плохой ключ одной
строкой лога и завершается с кодом 64-69 (`compose/README.ru.md`, «Разбор
проблем»), а `deploy.sh up` сразу падает и называет сервис. Он же отказывает,
если `.env` включает оба профиля, — ещё до `pull`.

## Шаг 5. Развёртывание с ноутбука оператора (день N)

Вместо ручного `docker compose` на сервере удобнее гонять скрипт — он сам
подкладывает SQL-схему хранилища токенов, синхронизирует `compose/`, дёргает
`pull` + `up -d` и дожидается healthcheck'ов.

```
# провайдеры из COMPOSE_PROFILES сервера
scripts/deploy/deploy.sh --host user@server up

# плюс выдача токенов разработчикам (docker-compose.issuance.yml)
scripts/deploy/deploy.sh --host user@server --issuance up
```

`--mode` больше нет (удалён в 1.1.0; любое значение отклоняется). `up`
отказывает стеку, в котором `COMPOSE_PROFILES` не включает ни одного провайдера,
удаляет контейнер провайдера или фронта, которого `.env` больше не выбирает, и
выполняет `up -d --remove-orphans`. Эти проверки идут после синхронизации: если
одна из них отказывает, `compose/` уже синхронизирован, а ничего не скачано, не
запущено и не удалено. `up` также проверяет, что поднимет юнит автозапуска после
перезагрузки: отказывает, если голый `docker compose` не может разрезолвить
стек, и предупреждает, если после перезагрузки поднимутся другие шлюзы или те же
с другой конфигурацией (обычно — строка `COMPOSE_FILE`, не совпадающая с
`--issuance`).

**На хосте с выдачей токенов передавайте `--issuance` во все последующие
запуски** — `logs`, `status`, `down`, `restart` резолвят стек через этот список
файлов (`DEPLOY_ISSUANCE=1` тоже работает). Ему нужен `gateway/config.toml` в
каталоге развёртывания на сервере (за основу берите
`compose/gateway/config.toml.example`); без этого файла `up` отказывает до
синхронизации и запуска. Синхронизация этот файл никогда не загружает и не
перезаписывает. Для юнита автозапуска раскомментируйте в `.env`
`COMPOSE_FILE=docker-compose.yml:docker-compose.issuance.yml`. Настройка и ручная
команда с двумя файлами — `compose/README.ru.md`, «Выдача токенов
разработчикам».

Остальные подкоманды: `down` (тома сохраняются, спрашивает подтверждение),
`restart`, `logs`, `status`. Полезные флаги: `--dry-run`, `--yes`,
`--dir PATH`, `--force-unlock`.

Локальный `.env` наверх не уезжает никогда; серверный `.env` не трогается.
Ключи, сертификаты и `gateway/config.toml` из синхронизации исключены.

> Если разворачиваете руками, без скрипта, — перед первым стартом положите схему:
> `cp src/corp_llm_gateway/tokens/schema.sql compose/postgres/initdb/01-schema.sql`.
> Init-скрипты Postgres отрабатывают только на пустом томе, при первом запуске.

## Шаг 6. Переключатель — оракул на корп-vLLM

Оракул — это **условный fallback** в конце локального каскада детекции. Он
вызывается только при детерминированном попадании в газеттир, а не на каждый
запрос.

**Выключен по умолчанию** (`CORP_LLM_ORACLE_ENABLED=0`). В этом состоянии вызов
не делается никогда и `CORP_LLM_ENDPOINT` для детекции не нужен.

Включение:

```
CORP_LLM_ORACLE_ENABLED=1
CORP_LLM_ENDPOINT=https://<хост-корп-vllm>/v1    # обязателен, когда оракул включён
```

Три вещи, на которых спотыкаются:

- **Включить без доступного endpoint'а — уронить запросы на всех маршрутах**, а
  не только на `corp-*`: попадание в газеттир уйдёт на немаршрутизируемый
  placeholder-хост и запрос упадёт fail-closed. Сначала проверьте, что vLLM
  доступен.
- Маршруту `corp-*` провайдера `corp` `CORP_LLM_ENDPOINT` нужен **независимо**
  от этого флага.
- **Нельзя выключить одновременно оракул и локальный каскад.** При
  `CORP_LLM_ORACLE_ENABLED=0` и `CORP_LLM_LOCAL_FIRST=0` шлюз откажется
  стартовать — он не работает как no-op-санитайзер. `CORP_LLM_LOCAL_FIRST` на
  этом стеке не задан и по умолчанию равен `1`; просто не ставьте `0`.

Если корп-vLLM за внутренним CA — положите цепочку в
`compose/certs/corp-ca-bundle.pem` и раскомментируйте `CORP_LLM_CA_BUNDLE`.

## Шаг 7. Переключатель — сервис корп-NER

Удалённый NER-детектор, добавляемый в локальный каскад. Ходит **по сети**,
поэтому исключён из сегментов с кодом (иначе исходники ушли бы во внешний
сервис); локальные детекторы код сканировать продолжают.

**Выключен по умолчанию** (`CORP_NER_ENABLED=0`) — ни детектора, ни пробы
готовности, стек ведёт себя так, будто фичи не существует.

Включение — обе переменные вместе:

```
CORP_NER_ENABLED=1
CORP_NER_ENDPOINT=http://<хост-ner>:<порт>     # БАЗОВЫЙ url, клиент сам добавит /v1/analyze
```

- **Включено без endpoint'а — отказ на старте**, а не тихий пропуск.
- **Нужна сборка из исходников** (шаг 3): на опубликованном `1.0.0-rc.6` эти
  переменные не делают ничего.
- Тюнинг (`CORP_NER_TIMEOUT_S`, `CORP_NER_MAX_TEXTS`, `CORP_NER_MAX_INPUT_CHARS`,
  `CORP_NER_CA_BUNDLE`) — оставляйте строки **закомментированными**, а не
  пустыми: пустая переменная окружения побеждает конфиг-файл. Значения по
  умолчанию: 30 с, 256 текстов, 200000 символов, без CA.
- Вызов NER несёт **сырой пользовательский контент**, поэтому проверка TLS для
  него не отключается никогда. Внутренний CA — через `CORP_NER_CA_BUNDLE`.

Переключение любого из флагов (оракул, NER) **безопасно для кэша**: в ключ
входит отпечаток эффективной политики детекторов, поэтому записи с разными
настройками не пересекаются. Чистить кэш не нужно.

Не путайте `CORP_NER_ENABLED` (этот удалённый сервис) с `CORP_LLM_REQUIRE_NER`
(внутрипроцессные RU/EN-движки) — второй в production остаётся `1` в любом
случае.

## Шаг 8. Проверка после старта

```
docker compose ps                                   # все сервисы healthy
curl -fsS http://127.0.0.1:4000/healthz/live         # gateway-anthropic (4001 codex, 4002 corp)
docker compose logs --tail=100 gateway-anthropic     # или gateway-codex / gateway-corp
docker compose logs --tail=50 vector                 # аудит доставляется
```

Порты шлюзов (4000, 4001, 4002) публикуются **только на loopback**. Langfuse не
публикует хостовый порт вообще — до UI добираются через фронт
(`https://langfuse.<домен>`) или SSH-туннелем (проброс локального `3000`).

С включённым фронтом проверьте и с машины разработчика:
`curl -fsS https://gateway.<домен>/healthz/live` (для самоподписанного
сертификата добавьте `--cacert <CA>`, никогда не `-k`). Через фронт доступен
только `/healthz/live`; `/healthz/ready`, `/healthz/sanitization` и `/metrics`
отвечают только на loopback-портах.

## Шаг 9. Выдача командных токенов (`X-Corp-Auth`)

Идентичность команды — заголовок `X-Corp-Auth`. Он определяет, какие правила,
профиль и аудит применяются, и нужен **на любом провайдере**. Запрос без
валидного токена отклоняется. Токен работает на всех шлюзах хоста: база у них
общая.

```
gateway-admin team create --team-id team-x --name "Team X"
gateway-admin token issue --user alice --team team-x --ttl-days 30
gateway-admin token revoke --user alice
```

⚠️ Мутации под RBAC требуют либо `CORP_GATEWAY_ADMIN_TOKEN` (операторский JWT),
либо `CORP_GATEWAY_RBAC=0` (обход для отладки), и **ни то, ни другое не задано в
окружении ни одного контейнера шлюза**. Выставляйте на той машине, откуда запускаете CLI.
Подробности — `docs/ops/admin-cli.md`.

## Шаг 10. Подключение разработчика

**Claude Code на провайдере `anthropic`:**

```
export ANTHROPIC_AUTH_TOKEN='sk-ant-oat...'    # токен подписки разработчика
export ANTHROPIC_BASE_URL='https://gateway.<домен>'
export ANTHROPIC_CUSTOM_HEADERS='X-Corp-Auth: <токен команды>'
unset ANTHROPIC_API_KEY                        # иначе он перекроет подписку
claude
```

Принимаются только токены вида `sk-ant-oat…`; всё остальное — `401
E_PROVIDER_AUTH`.

`ANTHROPIC_BASE_URL` — HTTPS-origin фронта (шаг 4a): `https://gateway.<домен>`
при `nginx`, `https://<адрес>:<NGINX_PORT>` при `nginx-ports` (порт 443 можно не
указывать). Для сертификата от CA, которому ноутбук не доверяет, нужен
`NODE_EXTRA_CA_CERTS=<файл CA>`. Без фронта разработчик открывает SSH-туннель к
`127.0.0.1:4000` сервера и использует `http://localhost:4000`. Фронт обслуживает
только шлюз `NGINX_GATEWAY_UPSTREAM`; до остальных добираются через туннель. При включённой
выдаче `scripts/install.sh` получает командный токен через тот же origin
(`CORP_GATEWAY_URL`, `docs/ops/install.md`). Подсчёт токенов
(`/v1/messages/count_tokens`) на фронте отвечает 404 (а на туннеле шлюз отвечает
403): для Claude Code он вспомогательный.

**Codex на провайдере `codex`:** профиль из `docs/chatgpt-codex.ru.md`, с
`base_url` на порт 4001 (туннель) или на фронт, если
`NGINX_GATEWAY_UPSTREAM=gateway-codex`, и corp-токеном разработчика в
`X-Corp-Auth`. Токен ChatGPT Codex передаёт сам.

**Провайдер `corp`:** направьте клиента на порт 4002 (туннель), с именем модели
`corp-…` и `X-Corp-Auth`. `Authorization` клиента до корп-vLLM не доходит
никогда; подписочный токен туда всё равно не отправляйте.

## Что важно знать перед вводом в эксплуатацию

- **HTTPS даёт только фронт.** Порты шлюзов (4000-4002) слушают `127.0.0.1` без
  TLS. По сети разработчики попадают на шлюз только через фронт на nginx (шаг
  4a); без него — через SSH-туннель. Не публикуйте вместо этого эти порты за
  пределы loopback.
- **management-эндпоинты litellm отклоняются, на любом провайдере.** Без
  мастер-ключа litellm принимает любого как internal user, так что значительная
  часть `/key/*`, `/model/*`, `/user/*`, `/policies*`, `/guardrails*` и UI иначе
  отвечала бы любому, кто дошёл до порта. Route gate отвечает на них `403 E_ROUTE_BLOCKED`
  раньше, чем запрос увидит litellm, на любом пути внутрь (`docs/security.md`
  §14). Операторы работают через `gateway-admin`, а не через UI litellm.
- **Никакого недоверенного `docker run` на этом хосте.** Метка контейнера, по
  которой Vector отбирает записи аудита, публична: любой, кто может запускать
  контейнеры на этом хосте, может подделать записи. Это жёсткое требование
  модели развёртывания, а не рекомендация.
- **Аудит буферизуется, но не fail-closed.** Дисковый буфер Vector (по умолчанию
  1 ГиБ) переживает недоступность Langfuse; после его заполнения записи ждут в
  лог-файлах docker'а, то есть реальная граница долговечности — ротация логов
  (по умолчанию 100 МБ × 10). Если Langfuse может лежать дольше — поднимайте оба
  значения вместе.
- **Не выполнять `FLUSHDB` на redis шлюза.** Там лежат маппинги, без которых
  ответ не восстановится в исходный вид.
- **Виртуальных ключей litellm нет** (режим A удалён в 1.1.0), так что нет и
  учёта расходов на человека через litellm. Отзыв на разработчика — это corp-токен:
  `gateway-admin token revoke`.
